状态：阶段0设计文档
任务标识：`YT-A0-002`
文档性质：本文件定义可试玩体验、界面结构和用户路径，不包含 UI 实现。

## 2. 体验主张

一句话体验：

```text
你不是在读一篇盐铁会议介绍，而是以观察员身份进入始元六年的朝堂，
在地图、压力场、证据和关系网之间判断：国家为什么要垄断盐铁，贤良文学为什么反对。
```

作品必须呈现三层冲突：

- 利益冲突：边费、财政、商贾、百姓负担、地方豪强、国家控制。
- 价值冲突：儒家的德治/轻徭薄赋与法家/财政国家的秩序、功利和强制能力。
- 权力关系：霍光辅政格局下，桑弘羊、车千秋、贤良文学、上官桀集团与昭帝朝政的相互位置。

## 3. 首屏与主路径

首屏不是营销页。首屏直接进入“会议现场”：

- 左侧：汉代版图与财政压力地图，显示边郡、盐铁资源、交通和都城位置。
- 中央：朝堂压力场，以财政压力、民生反问和权力边界呈现争论方向。
- 右侧：当前辩题卡，例如“盐铁官营是否应罢？”。
- 底部：时间轴，从武帝财政扩张到始元六年会议，再到罢榷酤和后世评价。

用户主路径：

1. 进入会议现场，阅读 30 秒背景卡。
2. 选择一个辩题：盐铁、均输、平准、酒榷、边防财政、民生与道德。
3. 分别听取双方立场，每个立场必须能展开原文证据。
4. 打开地图或关系网，理解政策为何不是抽象争论。
5. 形成一张判断卡：事实、推断、争议、个人反思、行动/不行动类比。
6. 可选查看“当代回声”，通过知乎接口搜索现代讨论，但界面明确标注它不是历史证据。

## 4. 功能区

### 4.1 会议现场

- 展示当前辩题、发言轮次、压力方向和证据摘要。
- 用户可切换“财政视角”“民生视角”“权力视角”“价值视角”。
- 每个发言都必须标记：原文事实、转述、策展解释、争议。

### 4.2 汉代地图

地图不追求 GIS 精确，而追求历史理解：

- 都城、边郡、盐铁资源、交通线、财政压力区。
- 地图图层从 `MapLayer` 读取，不硬编码主题。
- 用户点击图层点位时展示相关 EvidenceUnit。

### 4.3 辩题时间线

- 武帝财政政策背景。
- 始元六年会议。
- 罢酒榷而不全罢盐铁均输。
- 后世对盐铁政策和《盐铁论》的评价。

### 4.4 角色与权力网

角色卡包含：

- 身份、立场、利益约束、价值词、代表证据。
- 与其他角色的关系边：支持、制衡、上下级、政治风险、利益一致或价值冲突。

权力网必须避免戏剧化过度推断。凡非史料明言的关系，默认标注为 `contextual_inference` 或 `interpretive_hypothesis`。

### 4.5 证据室

- 支持按辩题、角色、来源、价值轴、政策类型过滤。
- 检索为轻量词法检索或预设路径检索，不使用运行时向量库。
- 若无证据，返回“档案不足”，不得让模型补答。

### 4.6 判断卡

判断卡是作品的认知出口：

- 原文事实：必须有 EvidenceUnit。
- 模型/策展推断：必须说明推断路径。
- 争议观点：必须说明争议主体或证据缺口。
- 个人反思：由用户选择或编辑。
- 行动出口：形成一个当代类比的“谨慎行动”“不行动”或“继续研究”，但不得把历史结论直接套用到现实政策。

## 5. 外部知乎接口体验

知乎接口只出现在“当代回声”区：

- `zhihu_search`：搜索知乎站内关于盐铁论、国家垄断、财政伦理等讨论。
- `global_search`：补充公开网络材料。
- `hot_list`：可选展示当前公共议题，帮助用户理解为什么古代财政伦理仍有现实回声。
- `zhida`：只用于现代解释或用户追问，不写入历史证据包。

接口失败时：

- 主体验继续可用。
- 显示“外部回声暂不可用”。
- 不影响已生成的历史判断卡。

## 6. 视觉与可用性要求

- 历史叙事感来自地图、朝堂压力场、卷轴式证据和暗色/纸色分层，但不得牺牲可读性。
- 页面要像工具而不是宣传页：用户一进来即可操作。
- 地图和关系网必须有稳定尺寸，避免文字和节点重叠。
- 移动端优先保留：辩题卡、发言、证据展开、判断卡；地图和关系网降级为可横滑视图。
- 所有按钮和控件使用清晰图标或短标签；不得用大段说明文字替代交互。

## 7. MVP 验收场景

- 用户能回答：会议何时发生、谁在争论、争论什么、结果是什么。
- 用户能区分：桑弘羊财政理由、贤良文学道德理由、霍光政治背景。
- 用户能从至少三条来源打开证据：《盐铁论》《资治通鉴》《汉书》或《史记》。
- 用户能生成判断卡，并看到哪些内容是事实、推断、争议和个人反思。
- 用户断网或无知乎 Access Secret 时，核心历史复原仍完整可玩。

## 8. V2.2 历史背景与扩展辩论过程层

任务标识：`YT-V2-007`

V2.2 的主体验先保留历史背景入场，再进入更细的朝堂辩论。用户应先理解盐铁、均输、平准与边防财政如何形成会议压力，再进入儒法价值冲突和权力关系。

历史背景入场：

- 武帝余响：盐铁、均输、平准等财政制度已经运转多年，会议不是孤立事件。
- 诏问民疾苦：始元六年的会议由询问贤良文学和民间疾苦进入朝堂。

正式辩论与收束：

- 边费压境：桑弘羊把盐铁、均输和边防财政绑定，代表国家能力立场。
- 废止之请：贤良文学首先请求罢盐铁、酒榷和均输，把矛头指向官营制度。
- 与民争利：贤良文学把政策批判转向德治与民生痛感，反对官府入市逐利。
- 均输之辩：大夫强调平物价与转运能力，贤良文学强调实践中的盘剥风险。
- 义利相击：双方冲突从政策可行性升高为儒法价值边界。
- 本末之争：农桑为本、商工流通与国家秩序之间的冲突被场景化呈现。
- 霍光阴影：权力关系压住辩论边界，提示会议并非中立公共空间。
- 退朝余波：以“榷酤可罢，盐铁未废”收束，进入用户的退朝案牍。

体验约束：

- 每一幕必须包含发言者或叙事视角、立场、一句短发言、视觉模式和至少一条 EvidenceUnit。
- 证据以“证据印记”出现，默认不铺满界面；用户点击后再展开原文、转述和出处。
- 儒法冲突必须通过张力轴、压力方向和证据浮现呈现，避免靠大段说明文字完成。
- 判断卡在 V2.2 中继续命名为“退朝案牍”，它是体验收束而非普通表单。
- 关闭声音时，历史背景、扩展辩论、证据展开和退朝案牍仍必须完整可用。

## 9. V2.3 五幕显影与全文争点矩阵

任务标识：`YT-V2-009`

V2.3 的核心原则是：五幕主线负责体验，不负责替代《盐铁论》全文阅读。全文复杂性通过争点矩阵保持可追溯，避免把产品重新做成逐篇导读或文献阅读辅助品。

主路径固定为：

- 历史入场一：武帝以来财政机器已经运行。
- 历史入场二：始元六年会议以诏问民疾苦进入朝堂。
- 财政先声：边防、府库、盐铁和均输让国家能力先占上风。
- 民生反击：贤良文学以“与民争利”把财政技术推向治理正当性。
- 义利显形：争论升高为国家能否以“利”为治理逻辑。
- 治道复杂化：引入荀子、管子等思想透镜，打破简单儒法二分。
- 权力遮蔽：霍光格局和后续政治危机显示公共辩论的政治边界。
- 退朝案牍：用户根据五幕选择和个人反思形成收束。

全文争点矩阵不进入主线播放，而以短标签旁路呈现。矩阵至少覆盖盐铁、酒榷、均输、平准、边防、农桑、商工、奢俭、吏治、教化、义利、权力、后世评价。每个争点映射到一个或多个主线幕，说明《盐铁论》相关内容在思想结构中的位置。

哲学辅助材料只能作为“思想透镜”使用，不得冒充盐铁会议事实。新增透镜证据使用现有 EvidenceUnit Schema，通过 `value_tags` 标记 `philosophy_lens`、`yi_li`、`institutional_order`、`statecraft` 等；历史事实仍以《盐铁论》《史记》《汉书》《资治通鉴》及公版后世评价为主。

验收重点：

- 用户不打开证据室也能走完 2 幕历史入场、5 幕思想显影和退朝案牍。
- 每个思想幕同时绑定历史证据和哲学透镜证据。
- 张力轴必须呈现“进入本幕前”和“本幕之后”的变化，而不是静态标签。
- 用户在五幕中的价值选择必须汇入退朝案牍，但不得改写历史事实。
## 10. V2.4 全文章节冲突图谱

任务标识：`YT-V2-010`

V2.4 修正 V2.3 的覆盖不足：五幕主线只负责沉浸与思想显影，不再被视为《盐铁论》全文内容的替代。作品新增“诸篇争锋”第二层体验，以章节冲突图谱覆盖《盐铁论》六十篇。维基文库目录实际为十卷六十篇，因此产品按十卷顺序排列，不强行改写为十二卷。

章节图谱原则：

- 每篇都有一个冲突短题，而不是只显示目录名。
- 每篇至少绑定一条《盐铁论》直接史证 EvidenceUnit。
- 每篇至少绑定一条哲学透镜 EvidenceUnit；透镜只解释思想结构，不作为会议事实。
- 图谱入口不打断主线，用户可以在任一幕打开“诸篇争锋”，从章节节点进入证据抽屉。
- 退朝案牍记录用户访问过的章节争点，使最终判断不只来自五幕主线，也来自用户主动查看的全文节点。

交付约束：

- 不新增运行时 RAG、向量库或大模型史实生成。
- 不修改公共 Schema，不新增后端 API。
- 交付包只保留精选短摘、转述、出处和解释透镜，不交付完整《盐铁论》原文。

## 11. V2.5 哲学透镜层

任务标识：`YT-V2-011`

V2.5 的目标不是继续扩大章节数量，而是提高“诸篇争锋”的解释能力。五幕主线和六十篇图谱已经解决覆盖问题；哲学透镜层负责让用户看到同一场政策争论可以被义利、民本、礼法、法术、富国、农战、灾异、徭役等不同思想传统重新照亮。

透镜材料原则：
- 透镜数量从 10 条扩展到 24 条以上，但保持精选短摘，不做哲学文献库。
- 透镜只能解释思想结构，不得作为盐铁会议事实证据；事实链仍以《盐铁论》《汉书》《史记》《资治通鉴》等史料为主。
- 每条透镜必须有 `philosophy_lens` 标签、出处定位、短摘、白话转述、版权说明和边界说明。
- 每个章节节点至少绑定一个合法透镜，重点章节可绑定两个或三个互相拉扯的透镜。

体验呈现原则：
- 章节详情不再只显示“透镜 1”，而是显示“用什么眼光看这场争论”。
- 透镜按钮使用短名，例如“义利之辨”“食兵民信”“法不阿贵”“饥寒劳苦”，让用户先获得解释角度，再决定是否展开原文。
- 证据抽屉打开透镜时必须标注“思想透镜，不是会议事实”。
- 退朝案牍应汇总用户访问过的章节和透镜类型，使最终判断体现用户借用了哪些哲学视角。

## 12. V3.0 朝堂压力开场纵切片

任务标识：`YT-V3-001`

V3.0 的目标是把用户进入产品的前一分钟从“看见界面”升级为“进入历史压力”。它不扩展史料，不新增 RAG、向量库或运行时模型生成，也不安装新的前端框架；只在现有 Canvas、SVG、CSS 动画和 Web Audio 上做体验纵切片。

体验原则：
- 动画必须服务叙事：长安、边塞、盐铁、均输和府库压力逐步显影，让财政机器先于辩论出现。
- 地图压力线汇入长安后，画面转入朝堂压力场；不使用抽象人形轮廓，也不使用席位、案几、竹简等器物锚点。
- 桑弘羊一侧强调府库、边费和国家能力；贤良文学一侧强调农桑、民户和疾苦；霍光只以屏风阴影和压暗表现权力边界。
- 证据和哲学透镜仍保持轻量浮现，点击后进入既有证据抽屉，不铺满界面。
- 关闭声音时，动态地图、朝堂压力场、证据浮现和退朝案牍仍必须完整可用。

交付边界：
- 不修改 `evidence_pack.json`、公共 Schema 或 `/api/yantie/*`。
- 不引入 React、Vite、Three.js、GSAP、PixiJS、Howler 等新依赖。
- V3.0 只证明沉浸式方向成立，不一次性制作全量人物立绘、配音或复杂资产库。

## 13. V3.1 汉昭帝时期叙事地图与开场减噪

任务标识：`YT-V3-002`

V3.1 修正 V3.0 在 V2 界面上直接叠加动画造成的凌乱问题。开场不再同时展示章节图谱、证据入口、判断区和人物表达，而是先成为独立的汉昭帝时期复原叙事地图：长安、北边压力、盐铁山海之利和均输路线依次汇入朝堂，用户完成这段入场后再进入五幕主体验。

地图原则：
- 地图采用“历史地理资料参考 + 本地简化 SVG 复原”的方式，呈现关中、河西/北边、山东腹地、江淮与山海资源方向。
- GIS 技术路线采用开源方案优先：后续正式地图层可用 MapLibre GL JS 加本地 GeoJSON/PMTiles，数据源优先选择许可清晰的开放历史地理或自绘矢量层。
- 当前交付仍使用本地简化 SVG 矢量层，风格上向真实历史地图靠近；边界不伪装成汉昭帝时期的原始测绘图。
- CHGIS 等历史地理资料只作为复原参考，不把原始 SHP、GeoJSON 或数据库打包进产品交付；交付中保留来源说明和复原边界说明。若后续使用第三方历史 GIS 数据，必须先确认开源/商用许可。
- 现有 `MapLayer` 仍是叙事点位与证据绑定来源；新底图只负责空间真实感，不新增历史事实来源。

开场减噪原则：
- 序章阶段只保留地图、一句短旁白和“进入朝堂”动作。
- 序章阶段隐藏证据按钮、诸篇争锋入口、判断 Dock、复杂 HUD 和人物表达。
- 压力线只保留边费、盐铁、均输三条主线；进入朝堂后只用财政压力、民生反问和权力边界三组方向线表达冲突。
- 序章结束后恢复 V2.5 的五幕主线、六十篇章节冲突图谱、哲学透镜、证据抽屉和退朝案牍。

## 14. V3.2 历史压力入场与用户站队

任务标识：`YT-V3-003`

V3.2 的目标是把用户从旁观者变成带着立场进入历史的人。开场不再先介绍人物或会议，而是让压力先发生：武帝余响、北边急报、府库吃紧、盐铁入官、民户承压、未央召议逐步推进。用户在看到压力分布后，必须选择一个初始身份：国家财政官、边疆将军、地方百姓或盐铁商人，然后才能进入会议主线。

体验原则：
- 背景必须“发生”，不能只被说明；前一分钟只显示地图、压力条、短旁白和证据支持强度。
- 初始身份只改变用户进入视角，不改变历史事实；身份选择写入最终退朝案牍。
- 历史导演是确定性的体验编排层，不是 Agent，不调用模型，不即时生成史实。
- 压力维度固定为边防、府库、民生、商贾、权力；会议推进时这些压力重新分布。
- 每条导演旁白和核心争论句显示“证据支持强度”，并明确它不是绝对真相概率。
- 退朝案牍必须展示观点变化图：初始身份、五幕选择、最终倾向、个人反思。

交付边界：
- 不改 `/api/yantie/*`，观点变化写入既有 `personal_reflection`。
- 不改 `evidence_pack.json`、公共 Schema 或运行态 `library/` 数据。
- 不重新引入人物、席位、剪影或器物锚点；朝堂表达继续使用压力场。

## 15. V3.3 历史复原即时反馈

任务标识：`YT-V3-004`

V3.3 的目标是让用户打开页面的前 30 秒就感到“历史正在被复原”，而不是等待一个历史知识页面加载完成。本轮仍基于 V3.2，不改 API、不改证据包、不引入 React/Vite/GIS SDK/动画库，只在现有静态前端运行时中加入轻量即时反馈。

体验原则：
- 加载不是 `Loading`，而是“汉昭帝始元六年、史料、地图、路线、朝堂”逐步显影。
- 第一秒地图即可互动；长安、北边、金城、盐铁资源、均输路线都是可 hover、可点击的复原热点。
- 热点反馈回答“为什么这里重要”，不做百科式长说明。
- 地图必须持续“活着”：边费、盐铁、均输路线有缓慢流动的可见运输点。
- 证据入口改为“发现竹简 / 发现案卷”，打开后仍是原有 EvidenceUnit，不改变证据边界。
- 声音仍使用本地 Web Audio 合成，只做轻量环境反馈；静音时体验完整。

交付边界：
- 不新增外部依赖，不接实时模型，不生成史实。
- 即时反馈只编排现有证据与策展文案；它是体验层，不是新的知识来源。
- 移动端必须保持无横向溢出，热点反馈不得遮挡继续推进的主动作。

## 16. GitHub Pages 静态发布

任务标识：`YT-V3-005`

静态发布版本用于解决 `workers.dev` 在中国大陆访问不稳定的问题。它不再依赖 FastAPI、Cloudflare Worker 或任何运行时后端，而是把当前盐铁会议体验导出到 `docs/yantie/`，由 GitHub Pages 直接托管。

交付原则：
- `docs/yantie/index.html` 使用同一套沉浸式 UI，但在 `<html>` 上标记 `data-yantie-runtime="static"`。
- 静态版只读取 `docs/yantie/data/evidence_pack.json`，浏览器内模拟原有 `/api/yantie/*` 的只读响应。
- 搜索、证据展开、章节图谱、哲学透镜和退朝案牍均在浏览器本地完成；判断卡不写入服务器，也不改写证据包。
- 静态版不调用 Cloudflare、知乎接口、外部模型、RAG、向量库或实时生成史实。
- FastAPI 版仍保留 `/yantie` 与 `/api/yantie/*`，用于本地开发、测试和后续需要后端能力的部署。

发布路径：
- 运行 `export_yantie_static_site()` 生成 `docs/yantie/`。
- GitHub Pages 选择从 `docs/` 目录发布。
- 发布后访问路径为 `https://<github-user>.github.io/<repo>/yantie/`。

验收要求：
- `docs/yantie/index.html`、`docs/yantie/data/evidence_pack.json` 和 `.nojekyll` 必须存在。
- 静态 HTML 必须包含 `loadStaticPack`、`getStaticData`、`staticSearchEvidence`、`createStaticJudgmentCard`。
- 页面不得依赖 `/api/yantie/*` 才能完成主体验；API 常量可以保留给本地模式使用。
- 静态版与 API 版使用同一个证据包，不产生两套历史事实来源。

## 17. 三段式叙事音乐

任务标识：`YT-V3-006`

音乐层用于增强“历史现场正在复原”的即时体验，但不作为知识来源，也不影响静音用户完成主流程。由于现代浏览器会限制未经用户交互的有声自动播放，产品使用“带声进入”作为音频解锁动作；一旦用户开启声音，后续音乐会随剧情自动切换。

音乐资产：
- `assets/audio/narrative.mp3`：用于历史复原、地图显影、压力入场和站位选择。
- `assets/audio/debate.mp3`：用于财政压力、民生反击、义利冲突和权力遮蔽等高潮辩论段落。
- `assets/audio/reflection.mp3`：用于治道复杂化、退朝案牍和个人反思。

体验原则：
- 三段音乐均为本地静态资产，不调用外部音乐模型、流媒体服务或运行时生成。
- 音轨切换使用淡入淡出，不硬切。
- 关闭声音后，Canvas、SVG、证据、章节图谱和退朝案牍仍完整可用。
- GitHub Pages 静态导出必须携带 `docs/yantie/assets/audio/` 下的三段音频。

## 18. 移动端地图优先入口

任务标识：`YT-V3-007`

手机端首页不得只是桌面界面的缩小版。压力入场阶段的首要体验是“地图正在复原”，因此移动端采用地图优先布局：地图固定铺满视口，叙事文字压缩为底部短抽屉，压力分布变成紧凑条，不再用多个大面板遮挡地图。

移动端原则：
- 序章阶段地图使用移动端安全取景，完整纳入底部抽屉上方的可视区域，避免裁切越界或把汉代版图压成一条横图。
- 底部叙事抽屉只显示标题、两行旁白和一个主动作；“发现竹简”“诸篇争锋”“回看”等次要入口在序章阶段隐藏。
- 压力入场只保留时间与五条压力条，隐藏长说明和支持强度细节；站位选择阶段再展开身份卡。
- 复原进度改成顶部细条，不占用地图主体区域。
- 证据抽屉在手机端必须全屏并高于地图、章节图谱和底部抽屉，关闭后回到地图现场。
- 桌面端保持原有双栏沉浸布局，不受移动端规则影响。

## 19. V3.4 交互与显示效果改进评估

任务标识：`YT-V3-008`

价值：把当前“可进入、可完成”的盐铁会议体验继续推进到“第一分钟有记忆点、全过程少干扰、最终判断有仪式感”。本节只定义后续 UX 与架构边界，不要求立即重构前端框架。

依赖：V3.1 叙事地图、V3.2 历史压力入场、V3.3 即时反馈、GitHub Pages 静态发布、三段式音乐和移动端地图优先入口。

允许修改范围：后续实施时仍优先限定在 `metaos/yantie/web.py`、`test/test_yantie_ui.py` 和本体验文档；若引入独立前端工程，必须另立任务并更新 API/发布契约。

禁止修改范围：不因 UX 打磨修改公共 Schema、运行态 `library/` 数据、根配置或证据包事实内容；不使用运行时模型补写史实。

输入：现有 `evidence_pack.json`、五幕主线、六十篇争点图谱、地图热点、身份站位、证据抽屉、退朝案牍和本地音乐资产。

输出：一组可逐步实施的交互改进原则、当前架构承载边界和未来重构触发条件。

接口：不新增 `/api/yantie/*`；静态版继续通过浏览器本地读取证据包和模拟只读 API。

### 19.1 交互改进空间

优先级从高到低：

- 第一分钟反馈：进入页面后立即让用户感到“历史正在复原”，地图显影、压力线流动、热点可点、点击后即时回应。加载、地图、证据和声音都应服务“复原感”，不出现普通软件式等待体验。
- 单一焦点原则：同一时刻只突出一个主要任务，例如“看地图压力”“选择身份”“经历一幕冲突”“查看一份证据”。地图、压力条、问答框、底部抽屉、章节入口和判断区不得同时争夺注意力。
- 地图分层：保留长安、北边、盐铁、均输等核心点位，但把地图逐步升级为可切换的叙事图层：空间地图、财政压力图、运输图、权力关系图和思想冲突图。
- 热点问答：地图点位点击后先给一句“为什么这里重要”，再允许展开史证或透镜；长文本必须在信息框内完整可读并可滚动，不能遮挡主动作。
- 身份影响：国家财政官、边疆将军、地方百姓和盐铁商人的选择不改写历史事实，但应影响旁白、压力权重、默认立场和退朝案牍中的观点变化轨迹。
- 辩论可视化：财政、民生、义利、治道、权力五类张力应以动态变化表达，而不是只靠文字说明。用户应看见冲突如何从财政技术问题逐渐升级为治道与权力问题。
- 证据发现感：证据入口继续从“查看证据”转为“发现竹简 / 案卷展开”。默认展示摘要和来源，原文、转述、哲学透镜和边界说明按需展开。
- 退朝案牍仪式感：最终不是普通表单，而是退朝后的个人案牍，必须汇总初始身份、关键动摇、访问过的史证和透镜、最终判断和未解决的矛盾。

### 19.2 显示效果改进空间

- 移动端继续采用地图优先，但所有浮层都必须满足：不横向溢出、可滚动、可关闭、不会挡住“继续推进”主动作。
- 地图不追求现代 GIS 精确边界，但应更接近历史地图质感：低饱和纸色、清晰地理骨架、少量动态运输线、少量可识别资源点。
- 文字层透明度、背景模糊和尺寸必须服务可读性，不用大面积深色面板遮死地图。
- 音乐与声音只作为环境层：叙事、辩论、反思三段音乐按阶段淡入淡出；静音时全部视觉与文本体验完整。
- 所有核心 UI 元素必须有稳定尺寸，避免 hover、点击、证据展开或长文本导致地图、按钮、抽屉跳动。

### 19.3 当前架构承载能力

当前 `FastAPI + 静态前端 + SVG/Canvas/CSS/Web Audio + evidence_pack.json + GitHub Pages 静态导出` 能承载以下改进：

- 地图显影、压力线流动、热点问答、镜头聚焦等轻量 SVG/CSS/Canvas 动画。
- 身份选择影响旁白、压力权重、默认立场和最终退朝案牍。
- 证据抽屉、哲学透镜、六十篇争点图谱和本地全文轻量检索。
- 三段本地音乐、轻量音效和静音降级。
- 移动端布局、底部抽屉、全屏证据层和静态发布。

当前架构不适合长期承载以下复杂化方向：

- 大规模人物立绘状态、复杂骨骼动画、Lottie 批量资产或多角色表演调度。
- 多分支剧情编辑器、可视化编排台、多人互动或复杂状态回放。
- MapLibre GL JS、PMTiles、GeoJSON 图层管理和真实 GIS 风格地图服务。
- 需要独立打包、按需加载、资源预取和复杂组件测试的大型前端应用。

### 19.4 重构触发条件

在以下任一条件成立前，不更换为 React/Vite/TypeScript：

- 前端状态超过单页脚本可维护范围，出现多个复杂互斥状态、跨视图回放或可视化编辑需求。
- 地图从本地叙事 SVG 升级为 MapLibre/PMTiles/GeoJSON 图层系统。
- 动画资产从少量 CSS/SVG 过渡到批量 Lottie、角色立绘、复杂场景时间轴。
- 需要组件级测试、资源分包、懒加载和独立构建流水线。

若触发重构，目标不是推翻现有体验，而是把当前静态纵切片迁移为独立前端工程；证据包、历史事实边界、静态可发布原则和“AI 不即时生成史实”的约束必须继续保留。

验收标准：
- 文档能清楚解释当前 UX 还有哪些可改进空间。
- 文档能清楚说明现有架构可承载的改进和不可承载的复杂化方向。
- 后续实施任务可以直接引用本节拆分为小步 UI 改进，而不是一次性重做。

测试命令：
- `git diff --check -- docs/YANTIE_PRODUCT_EXPERIENCE.md`

回滚方式：
- 直接 revert 本节文档追加，不影响代码、静态发布或证据包。

文档更新：
- 本节即为体验文档更新；若后续实际引入新前端工程、GIS SDK 或动画资产库，必须同步更新 API 契约、发布路径和任务拆分文档。

## 20. V3.5 历史经历化体验改造

任务标识：`YT-V3-009`

价值：把用户从“学习盐铁会议”进一步推向“在不知道结局的情况下经历盐铁会议”。本轮核心不是增加史料或功能，而是调整体验节奏：让压力先发生、身份从判断中生成、选择产生后果、权力通过沉默出现，最终让退朝案牍成为一次判断的仪式性收束。

依赖：V3.4 交互与显示效果评估、现有历史压力入场、身份站位、五幕主线、六十篇争点图谱、史证抽屉、哲学透镜、退朝案牍和三段式音乐。

允许修改范围：后续实施时优先限定在 `metaos/yantie/web.py`、`test/test_yantie_ui.py` 和本体验文档；若需要新增复杂状态管理或独立前端工程，必须另立架构任务。

禁止修改范围：不修改公共 Schema、运行态 `library/` 数据、根配置、原始证据事实和 `/api/yantie/*` 契约；不使用运行时模型即时生成史实。

输入：现有证据包、地图热点、压力时间线、身份角色、冲突幕、用户选择和本地音频资产。

输出：一组“经历优先”的交互设计原则和可拆分实施任务。

接口：继续使用现有静态证据包和浏览器本地状态；用户选择仍汇入既有退朝案牍和 `personal_reflection`，不新增后端接口。

### 20.1 体验原则

- 第一幕只出现“天下”，不出现桑弘羊、贤良文学、霍光、席位或人物介绍。开场只表现边报、府库、盐铁、均输、民生压力如何逼近长安。
- 背景不再解释，而是发生。用短句、地图压力、运输线中断、府库变化和声音停顿，让用户先感到“国家不得不议”，再知道“盐铁会议是什么”。
- 身份不直接让用户挑选，而应先让用户做一个现实判断，再由系统生成“你更接近哪一种立场”。例如先问昭帝只能优先处理边防、减税、盐铁私营或府库不足中的哪一项，再映射到财政官、边疆将军、地方百姓或盐铁商人。
- 关键选择应有轻量不可逆性。用户可以反思和改变最终判断，但早期选择应被记录，并在后续压力变化中产生对照，避免体验变成随时重填的问卷。
- 让“沉默”进入产品。权力不必总通过说明文字呈现；霍光回合可以通过画面变暗、声音压低、短暂停顿和一句“霍光未发一言”表达政治边界。
- 允许用户误判。产品不应让用户一开始就得到最优答案，而应让用户在财政压力、民生痛感、边防风险和权力阴影之间发生动摇。
- 证据继续从“查看”转为“发现”。竹简、案卷、奏章、史官记录等视觉提示只负责体验语义，展开后仍回到 EvidenceUnit，不改变史实边界。
- 退朝案牍不只是总结页，而是一次自动生成的退朝记录：初持何见、何处动摇、所据何证、仍有何疑、最后盖印收束。
- “历史不知道自己是历史”。体验过程中不提前告诉用户盐铁会议影响后世两千年；直到退朝之后，才以短句提示今天仍在争论国家、市场、民生与公共判断。

### 20.2 建议体验节奏

V3.5 的主路径应采用电影式节奏，而不是持续信息输入：

1. 历史压力：地图展开，北边急报、府库吃紧、盐铁入官、均输路线、民户承压依次发生。
2. 第一次判断：用户在不知道会议走向的情况下，先对边防、减税、盐铁私营或府库压力作取舍。
3. 身份生成：系统根据第一次判断生成初始立场，而不是让用户从列表中挑身份。
4. 入朝：会议开始，财政理由先出现。
5. 第一次冲突：民生反击出现，用户第一次动摇或坚持。
6. 证据发现：短暂发现一份竹简或案卷，展开后显示可定位史证。
7. 第二次冲突：义利、治道与国家能力复杂化。
8. 沉默：霍光阴影出现，声音与画面短暂停顿。
9. 退朝：不再增加新信息，只生成个人案牍。
10. 后世回声：最后才提示这场争论没有真正结束。

### 20.3 具体改进任务

- `YT-V3-009A`：开场压力重编排。删除第一分钟内的人物/席位信息，只保留地图、压力、短句和声音停顿。
- `YT-V3-009B`：身份生成式入场。把“选择身份”改为“先作现实判断，再生成初始立场”，并记录到观点轨迹。
- `YT-V3-009C`：不可逆判断轨迹。早期选择不能被抹除，只能在后续案牍中显示“曾经持有/后来动摇/最终修正”。
- `YT-V3-009D`：霍光沉默段。通过停顿、暗场、压低音乐和短句表现权力边界。
- `YT-V3-009E`：误判与动摇反馈。把财政压力、民生压力和边防风险与用户选择发生对照，提示“你开始动摇”而不是直接评分。
- `YT-V3-009F`：证据发现化。把证据入口文案和动画改为竹简/案卷发现，但保持 EvidenceUnit 数据不变。
- `YT-V3-009G`：退朝案牍仪式化。生成自动书写、盖印、静音收束的最终记录。
- `YT-V3-009H`：后世回声延迟。退朝前不讲后世影响，退朝后只用一句短回声连接当代。

### 20.4 前端架构承载判断

当前前端架构可以承载 V3.5 的第一轮实现。理由是这些改进主要是体验编排，而不是新的技术平台：

- 压力入场、沉默、暗场、证据发现、退朝盖印都可以用现有 HTML/CSS/SVG/Canvas/Web Audio 完成。
- 身份生成和不可逆判断轨迹可以用现有浏览器本地状态完成，不需要后端写入或新 API。
- 误判与动摇反馈只是把用户选择与既有压力值、证据访问记录和五幕选择做确定性对照，不需要模型即时推理。
- 后世回声只是叙事收束，不影响证据包或史实来源。

但当前单文件静态前端会在以下情况下接近维护边界：

- 若每个身份都需要独立剧情分支、独立音乐轨、独立地图状态和多段回放，状态管理会迅速复杂。
- 若退朝案牍需要可编辑、可分享、可保存多次历史记录，静态本地状态会不够。
- 若证据发现变成大量动画资产、角色立绘和复杂时间轴，CSS/SVG 手写维护成本会过高。
- 若地图要升级为真实 GIS 图层、矢量瓦片或交互式交通/财政网络，则应引入独立前端工程和 MapLibre 方案。

结论：V3.5 的“体验节奏升级”可以继续基于当前架构完成，不需要立即切换 React/Vite。只有当产品从单条沉浸纵切片升级为多分支历史互动系统、复杂地图系统或资产密集型动画系统时，才应启动独立前端工程。

验收标准：
- 用户第一分钟不再学习人物，而是先经历历史压力。
- 用户身份来自一次现实判断，而不是直接从列表选择。
- 至少一个关键选择在退朝案牍中作为不可抹除的早期判断出现。
- 霍光/权力边界至少有一次通过沉默、暗场或声音变化呈现。
- 退朝案牍能显示初持、动摇、证据和最终判断。
- 所有新增体验仍可在静音、移动端和 GitHub Pages 静态版中完成。

测试命令：
- `git diff --check -- docs/YANTIE_PRODUCT_EXPERIENCE.md`

回滚方式：
- 删除本节或 revert 本节文档追加，不影响现有代码、证据包和静态发布。

文档更新：
- 本节为体验文档更新。后续若实施 `YT-V3-009A` 至 `YT-V3-009H`，每个任务必须同步更新本节状态或追加对应实现说明。

## 21. V3.6 视觉焦点与交互显示系统

任务标识：`YT-V3-010`

价值：在 V3.5 的“经历化节奏”之上，进一步解决界面层面的沉浸感问题。目标不是增加更多内容，而是让每一屏只有一个视觉中心，让地图、证据、朝堂、退朝案牍各自承担不同阶段的叙事焦点。用户不是在浏览一套历史资料，而是在一座会随着自己行动而变化的历史现场中行走。

依赖：V3.4 交互与显示效果评估、V3.5 历史经历化体验改造、现有叙事地图、压力时间线、证据抽屉、章节图谱、退朝案牍和三段式音乐。

允许修改范围：后续实施时优先限定在 `metaos/yantie/web.py`、`test/test_yantie_ui.py` 和本体验文档；如新增独立前端工程、地图 SDK 或动画资产库，必须另立架构任务。

禁止修改范围：不修改公共 Schema、运行态 `library/` 数据、根配置、证据包事实内容和 `/api/yantie/*` 契约；视觉动画不得引入新的历史事实。

输入：现有 HTML/CSS/SVG/Canvas/Web Audio 运行时、地图热点、压力值、证据包、章节图谱、身份状态和退朝案牍状态。

输出：一套视觉焦点、信息层级、地图镜头、动画语言、声音空间和架构承载边界的设计准则。

接口：不新增后端接口；所有显示效果仍由现有前端状态和静态证据包驱动。

### 21.1 核心 UX 原则

- 一屏只有一个视觉中心。地图、压力条、章节图谱、证据、哲学透镜和退朝案牍都重要，但不能同时重要。
- 地图不是背景，而是叙事舞台；按钮不是操作，而是进入历史的入口；证据不是附件，而是剧情的一部分；动画不是装饰，而是因果关系的表达；界面不是页面，而是导演镜头。
- 每次点击都应改变现场。用户点击盐铁、均输、长安、北边等热点时，至少应触发一个可见反馈：点位亮起、路线流动、压力变化、短句浮现或声音回应。
- 信息分层优先于弹窗堆叠。不同长度的信息必须使用不同容器，避免所有内容都进入同一个 Drawer。

### 21.2 视觉焦点阶段

主体验应按阶段切换视觉中心：

1. 入场：地图为唯一中心，只显示叙事地图、复原状态、少量压力反馈和主动作。
2. 入朝：地图退为背景，朝堂压力场成为中心。
3. 争论：张力轴、双方声音和当前压力 HUD 成为中心。
4. 发现证据：证据以竹简/案卷的方式短暂成为中心，展开后回到原文和出处。
5. 退朝：所有辅助 UI 退下，退朝案牍成为唯一中心。
6. 余韵：案牍淡出，地图恢复，只留“朝议已毕，天下未定”的后世回声。

验收时不得出现多个大型面板同时争夺注意力，尤其在移动端不得同时展示地图、压力条、问答框、章节入口和判断区。

### 21.3 地图镜头语言

地图需要从“平面信息图”升级为“导演镜头”：

- 入场镜头：从天下大势到关中，再到长安，最后进入未央宫朝堂。
- 热点镜头：点击长安、北边、盐铁资源或均输路线时，镜头轻微聚焦而不是只打开信息框。
- 因果镜头：点击盐铁资源后，盐铁点位先亮起，运输线开始流动，长安压力短暂变化，再出现一句短旁白。
- 退朝镜头：最终不直接结束，而是从案牍慢慢退回地图，让用户看到“会议结束，但天下未定”。

当前 SVG/CSS 可以用 `viewBox`、`transform`、`opacity` 和 CSS transition 模拟镜头推进；不必立即引入 MapLibre 或真实 GIS。

### 21.4 活地图与历史压力 HUD

地图应持续“呼吸”，但不能变成噪声：

- 运输线缓慢流动，用于表现盐铁、均输和边费的流向。
- 北边烽火轻微闪烁，用于表现边防压力。
- 长安使用低频呼吸光，用于表现压力汇入。
- 府库、民生、商贸、朝廷稳定等压力维度可在当前阶段以紧凑 HUD 显示。

压力 HUD 不是游戏数值，而是国家状态：

- 始元六年
- 边防
- 府库
- 民生
- 商贸
- 朝廷稳定

HUD 只显示趋势和相对强弱，不伪装成精确财政数据；所有数值均为叙事压力，不作为历史事实证据。

### 21.5 信息展示层级

所有信息不再默认进入 Drawer，而按长度和任务分层：

| 信息类型 | 展示方式 | 用途 |
| --- | --- | --- |
| 一句话反馈 | Tooltip / 地图短句 | 回答“这里为什么重要” |
| 中等说明 | Side Panel / 底部短抽屉 | 当前压力、身份、阶段提示 |
| 原文史证 | Drawer / 案卷抽屉 | EvidenceUnit、出处、转述、证据边界 |
| 全文结构 | Full Page / 专用章节图谱 | 六十篇争点矩阵、长列表和检索 |

移动端必须优先使用底部短抽屉和全屏证据层，避免右侧面板挤压地图。

### 21.6 字体、颜色与空间层级

字体层级应更大胆，减少“一片字”的感觉：

- 场景章名：用于阶段切换和退朝案牍标题。
- 当前问题：用于用户此刻必须面对的判断。
- 正文：只承载必要旁白和双方短句。
- 史证：比正文更克制，强调出处和可定位性。
- 出处/边界说明：小号但必须可读。

颜色不只表达古风，还要表达语义：

- 财政：青铜绿。
- 民生：土黄。
- 战争/边防：暗红。
- 权力：黑与深朱。
- 哲学：青色或冷灰。
- 证据：竹色与纸色。

空间层级使用 CSS 即可完成：

- 地图为底层。
- 运输线和压力为中层。
- 当前短句、选择和证据印记为前层。
- 证据抽屉、章节图谱和退朝案牍为顶层。

### 21.7 人物与符号表达

人物不应依赖头像或复杂立绘作为主要表达。优先使用：

- 名号与短句。
- 印章、笔迹、奏章、案卷。
- 声音、停顿、暗场。
- 极少量风格化剪影或席位暗示。

桑弘羊、贤良文学、霍光等人物的重点不是肖像，而是他们各自代表的压力、立场和权力位置。尤其霍光不宜用解释性人物卡表达，而应通过沉默、暗场和压迫感出现。

### 21.8 动画与声音语言

动画必须统一，不得每个模块各用一种语言：

- 地图：显影、推进、聚焦。
- 证据：卷开、落印、案卷展开。
- 人物/立场：浮现、退隐、压暗。
- 时间：滑动、停顿。
- 退朝：淡出、书写、盖印。

声音不只用音乐，还可加入轻量环境音：

- 地图：风声。
- 运输：马车或车轮。
- 朝堂：衣袖、低回声。
- 证据：竹简展开。
- 退朝：钟声或低频收束。

声音仍必须可关闭，关闭声音后视觉和文字体验完整。

### 21.9 具体改进任务

- `YT-V3-010A`：视觉焦点状态机。为地图、朝堂、证据、章节图谱和退朝案牍定义互斥焦点状态。
- `YT-V3-010B`：地图镜头推进。使用 SVG/CSS 模拟从天下到长安、再到朝堂的镜头语言。

## 22. V3.7 去软件感交互与移动端体验

任务标识：`YT-V3-011`

价值：降低用户“我正在操作一个网页”的感受，让每一次点击、滑动和展开都更像进入历史现场。V3.7 关注交互语言、主动作、移动端手势和界面容器，不新增史料、不改变证据边界。

依赖：V3.5 历史经历化体验改造、V3.6 视觉焦点与交互显示系统、现有地图热点、证据抽屉、章节图谱、退朝案牍和静态发布路径。

允许修改范围：后续实施时优先限定在 `metaos/yantie/web.py`、`test/test_yantie_ui.py` 和本体验文档；若单独实现移动端手势或视觉语言，应作为独立小任务推进。

禁止修改范围：不修改公共 Schema、运行态 `library/` 数据、根配置、证据包事实内容和 `/api/yantie/*` 契约；交互文案不得暗示未被证据支持的历史事实。

输入：现有前端状态、地图阶段、证据入口、章节图谱、退朝案牍、移动端布局规则和本地音频资产。

输出：一套减少“软件感”的交互命名、主动作、信息容器和移动端操作原则。

接口：不新增后端接口；所有变化均为前端交互编排和展示文案调整。

### 22.1 交互语言改造

功能名称应尽量从“软件模块”改为“历史行为”。用户理解的是自己正在做什么，而不是系统模块叫什么。

| 当前软件语言 | 建议历史语言 | 使用场景 |
| --- | --- | --- |
| 查看证据 | 发现竹简 / 展开案卷 | 打开 EvidenceUnit |
| 哲学透镜 | 换个角度看看 | 查看思想解释 |
| 判断卡 | 退朝之后 / 留下案牍 | 最终判断 |
| 章节图谱 | 今日争论 / 诸篇争锋 | 进入六十篇争点结构 |
| 热点问答 | 此地为何重要 | 地图点位说明 |
| 返回 | 回堂 / 回到现场 | 关闭旁路 |
| 完成 | 退朝 | 结束主体验 |

文案原则：
- 关键节点使用历史语境文案。
- 辅助和无障碍标签可以保留清晰的软件语义，避免用户迷路。
- 不为了古风牺牲可理解性。

### 22.2 主动作原则

每一幕只保留一个主要动作，其他入口弱化为旁路：

- 入场地图：主动作是“进入朝堂”。
- 身份生成：主动作是“作出取舍”。
- 财政先声：主动作是“听桑弘羊”。
- 民生反击：主动作是“听贤良文学”。
- 证据发现：主动作是“展开案卷”。
- 权力遮蔽：主动作是“继续退朝”。
- 退朝案牍：主动作是“盖印退朝”。

主动作必须在桌面和移动端都稳定可见；地图、章节、证据、透镜等旁路不得和主动作争夺视觉权重。

### 22.3 信息容器原则

减少“打开/关闭/打开/关闭”的疲劳。不同信息使用不同容器：

- 一句话反馈：地图短句或轻提示，不打断流程。
- 中等解释：侧栏或底部短抽屉，保留现场上下文。
- 原文史证：案卷抽屉，允许滚动和关闭。
- 长列表/全文结构：专用全屏视图，例如“诸篇争锋”。
- 关键判断：退朝案牍，不混入普通表单。

同一阶段最多出现三个区域：主视觉、当前事件、主动作。若出现第四个区域，必须折叠或降级为轻提示。

### 22.4 移动端重新设计原则

移动端不应只是桌面版缩小。手机端应采用“全屏现场 + 单句推进”的节奏：

- 地图全屏，底部只显示一句当前事件和一个主动作。
- 左右滑动可切换阶段，但必须保留可点击按钮，避免只依赖手势。
- 上滑可展开证据摘要，再上滑进入完整案卷。
- 长按地点或史证可查看出处，但出处仍必须可通过点击打开，兼顾可访问性。
- 所有底部抽屉必须避开系统安全区，并允许内部滚动。
- 移动端一屏不同时展示章节图谱、证据抽屉、压力 HUD 和判断区。

手势是增强体验，不是唯一入口；任何关键路径都必须可通过明确按钮完成。

### 22.5 低成本质感细节

优先实施低成本、高体感的微交互：

- 地图点位 hover 或点击时轻微放大。
- 压力条变化使用缓动，不瞬间跳变。
- 竹简/案卷展开使用 300-500ms 动画，不直接弹出。
- 每幕结束停顿 0.5 秒，再进入下一幕。
- 退朝案牍自动书写并盖印，而不是只显示“提交成功”。
- 点击均输或盐铁时，先触发路线流动，再出现解释。

这些细节必须服务叙事因果，不得变成装饰性动效。

### 22.6 前端架构承载判断

当前架构能够承载 V3.7 的第一轮实现：

- 文案替换、主动作状态、信息容器拆分和移动端底部抽屉都属于 HTML/CSS/JavaScript 调整。
- 地图点位放大、压力条缓动、案卷展开、盖印动画可用 CSS transition/keyframes 与现有 SVG 完成。
- 左右滑动、上滑展开、长按出处可用 Pointer Events / Touch Events 实现，不需要新框架。
- 现有静态 GitHub Pages 发布可继续使用，因为这些变化不依赖后端。

需要谨慎的部分：

- 手势交互会增加移动端状态复杂度，必须保留按钮兜底，并增加移动端验收。
- 如果后续大量引入复杂手势、拖拽、编辑、保存和分享，单文件脚本会变难维护。
- 如果要做系统性的组件库、响应式设计令牌和动画编排台，才需要考虑 React/Vite/TypeScript。

结论：V3.7 不需要更换前端架构。当前静态前端足以完成“减少软件感”和“移动端体验重排”的第一轮改进；只有当交互复杂度从单条体验升级为可编辑、多分支、可保存的应用时，才应启动独立前端工程。

验收标准：
- 页面关键按钮不再主要使用“查看/提交/返回”等软件感强的词。
- 每一幕只有一个主动作，旁路入口弱化。
- 不同长度信息使用不同容器，不全部进入 Drawer。
- 移动端主路径可通过按钮完成，手势只做增强。
- 手机端无横向溢出，底部抽屉不遮挡主动作。
- 静音和无手势操作时仍可完成完整体验。

测试命令：
- `git diff --check -- docs/YANTIE_PRODUCT_EXPERIENCE.md`

回滚方式：
- 删除本节或 revert 本节文档追加，不影响现有代码、证据包和静态发布。

文档更新：
- 本节为体验文档更新。后续实施 `YT-V3-011` 系列任务时，应同步追加移动端验收和交互文案变更记录。

## 23. V3.8 情绪曲线、参与感与体验导演

任务标识：`YT-V3-012`

价值：把现有“地图 -> 身份 -> 辩论 -> 证据 -> 判断”的功能流程，提升为一条有情绪起伏的历史经历。V3.8 的重点不是继续增加模块，而是让用户从“看历史资料”转向“在压力、停顿、选择和后果中经历一次朝议”。

依赖：
- `YT-V3-009` 历史经历化体验改造。
- `YT-V3-010` 视觉焦点与交互显示系统。
- `YT-V3-011` 去软件感交互与移动端体验。
- 现有叙事地图、压力状态、身份选择、证据包、退朝案牍和音乐控制。

允许修改范围：
- 本体验文档。
- 后续实施时可修改盐铁会议静态前端的页面结构、样式、交互脚本和轻量数据配置。
- 后续实施时可新增与体验状态相关的前端配置文件，例如场景表、情绪曲线表、动作反馈表。

禁止修改范围：
- 不新增史实结论。
- 不改变证据包的史料边界。
- 不引入运行时 RAG 或实时生成史实。
- 不改动 MetaOS 公共 Schema、数据库、迁移和根配置。
- 不把历史体验改造成复杂游戏数值系统。

输入：
- 现有盐铁会议体验流程。
- UX 评审意见：情绪曲线、参与感、场景化界面、证据发现、人物发言、沉默、即时反馈、统一动画语言、结尾余韵、引导系统和复盘反馈。

输出：
- 一套可实现的“体验导演层”设计。
- 一份前端架构承载判断。
- 一组后续可拆分实施的前端任务。

接口：
- `sceneId`：当前场景，例如 `map_opening`、`border_alert`、`court_entry`、`sang_statement`、`huo_silence`、`final_dossier`。
- `emotion`：当前目标情绪，例如 `curiosity`、`tension`、`reasoning`、`empathy`、`pressure`、`reflection`。
- `primaryAction`：当前场景唯一主动作。
- `feedbackEffects`：点击后的视觉、压力、声音和文案反馈。
- `reflectionProfile`：退朝后生成的用户判断倾向，不作为评分，只作为自我理解。

### 23.1 从流程表改为情绪曲线

现有流程已经完整，但用户感受到的情绪变化还不够明确。后续每一幕都应先定义“用户此刻应该感受到什么”，再决定动画、声音、布局和按钮。

建议建立情绪曲线：

| 阶段 | 用户情绪 | 触发方式 | 界面表现 |
|------|----------|----------|----------|
| 地图展开 | 好奇 | 天下缓慢显影 | 全屏地图、低信息密度 |
| 北边急报 | 紧张 | 边报、粮草、运输停滞 | 北境闪烁、压力上升、短句旁白 |
| 进入朝堂 | 被卷入 | 长安聚焦、未央宫出现 | 镜头推进、人物暂不铺满 |
| 桑弘羊发言 | 理性 | 财政与边防压力并置 | 青铜绿财政色、克制文字 |
| 贤良文学发言 | 共情 | 民户负担与地方声音出现 | 赭黄民生色、低速展开 |
| 霍光沉默 | 压抑 | 音乐停顿、界面变暗 | 三秒留白，只保留一句话 |
| 退朝案牍 | 反思 | 自动书写判断轨迹 | 纸面、墨迹、盖印 |
| 回到天下 | 余韵 | 地图退远、声音渐弱 | “朝议已毕”“天下未定” |

这条情绪曲线要成为所有设计取舍的上层约束。如果某个组件不能服务当前情绪，就应弱化、延后或移出当前屏幕。

### 23.2 参与感：让用户推动现场，而不是点击百科

地图阶段不应只让用户点击地点看说明，而应让用户在有限处境中作出轻量选择。

示例：

```text
北边急报
粮草不足

是否继续调粮入边？
```

用户选择后，先发生现场反馈，再出现解释：

1. 运输线亮起或中断。
2. 府库、边防、民生压力出现变化。
3. 音效或音乐层次改变。
4. 最后出现一句短文案解释结果。

这些选择不改变真实历史结论，只改变用户在体验中的压力感和判断轨迹。它们是“历史处境模拟”，不是架空剧情分支。

### 23.3 从 Dashboard 改为 Scene

后续界面不应同时展示地图、压力、时间轴、人物、证据、图谱、HUD 和判断区。V3.8 要求每个阶段最多保留三个区域：

- 主视觉：地图、朝堂、竹简或案牍。
- 当前事件：一句旁白、一段发言或一个问题。
- 主动作：唯一醒目的继续、选择或展开动作。

推荐场景序列：

```text
全屏地图
-> 北边急报
-> 长安聚焦
-> 朝堂发言
-> 竹简证据
-> 霍光沉默
-> 退朝案牍
-> 地图远景
```

章节图谱、全文结构、哲学透镜等深层内容仍然保留，但不应抢夺主路径的第一视觉焦点。

### 23.4 证据改为“发现”，人物改为“发言”

证据入口不再以“Drawer”作为用户感知，而应包装为历史动作：

- 地图上发现竹简。
- 点击后竹简展开。
- 原文和出处随卷面出现。
- 长文史证进入案卷视图。

人物表达也不应优先使用静态人物卡。桑弘羊、贤良文学和其他角色应先通过一句话进入场景，再允许用户查看补充说明。

示例：

```text
桑弘羊：
边费不可一日废。
```

人物卡、关系图和背景介绍作为旁路，不应成为人物首次出现的方式。

### 23.5 把“沉默”设计成界面事件

权力遮蔽不能只靠说明文字表达。霍光相关段落应成为一次明确的界面事件：

1. 当前辩论暂停。
2. 音乐降低或停止。
3. 朝堂界面变暗。
4. 三秒内不出现新按钮。
5. 出现短句：“霍光未发一言。”
6. 用户继续退朝。

这类留白要少用，但必须有明确节奏。它承担的不是装饰功能，而是让用户感到“真正的权力不一定在发言者那里”。

### 23.6 统一动画语言

V3.8 的动画应遵守统一语法，不为每个模块临时设计一套效果：

| 对象 | 动画语言 | 含义 |
|------|----------|------|
| 地图 | 推进、远退、显影 | 进入或离开历史现场 |
| 压力 | 缓动上升或下降 | 处境发生变化 |
| 人物 | 浮现、停顿 | 发言者进入朝堂 |
| 证据 | 卷开、落印 | 发现史料 |
| 判断 | 书写、划改 | 用户观点变化 |
| 退朝 | 淡出、盖印 | 朝议结束 |

所有动画必须可关闭或在 `prefers-reduced-motion` 下自动降级。

### 23.7 新用户引导：只引路，不讲课

第一次进入时可以加入“历史引路人”，但只出现一次，并且只说一件事：

```text
今天，你不是来学历史。
你将进入一次朝议。
```

随后引导消失，用户进入地图。引导系统不应变成教程，也不应解释所有功能。它的目标是调整用户预期：这里不是问答工具，也不是资料库。

### 23.8 退朝后的复盘反馈

退朝案牍之后，可以给用户一个轻量的判断倾向反馈。它不是评分，也不是人格测试，而是帮助用户看见自己的思考路径。

示例：

```text
你的判断更接近：

现实财政：██████
民生伦理：████
制度节制：█████
权力警惕：███████
```

反馈依据应来自用户在体验中的选择、证据查看和判断变化，而不是模型即时生成。文案必须避免“你属于某某派”这种过度标签化表达。

### 23.9 结尾余韵

体验不应以“完成”按钮结束。建议结尾采用自动退远：

```text
退朝案牍盖印
-> 音乐渐弱
-> 朝堂退远
-> 地图恢复天下
-> 朝议已毕
-> 停顿
-> 天下未定
```

如果需要呈现“两千年以后，人们仍在争论国家、市场、民生”，应放在退朝之后，而不是开场或过程中提前告诉用户。这能保留“历史不知道自己是历史”的体验。

### 23.10 前端架构承载判断

当前前端架构可以承载 V3.8 的第一轮改进。

理由：
- 情绪曲线可以做成静态配置表，不需要新后端。
- 场景推进、主动作、停顿、压力变化和退朝复盘都属于前端状态编排。
- 地图推进、竹简展开、压力缓动、界面变暗、盖印等效果可用现有 HTML/CSS/JavaScript/SVG 实现。
- 音乐停顿、音量渐弱和分段播放可继续使用现有前端音频控制。
- 用户选择和判断倾向可以保存在浏览器本地状态中，不需要账户系统。
- GitHub Pages 静态发布仍然可用。

需要警惕的边界：
- 如果后续要做大量分支剧情、可保存用户历史、多次复盘对比、分享海报、用户账户或跨设备同步，当前静态前端会开始吃力。
- 如果场景、动画、音效和状态继续快速增加，单文件脚本会变得难维护，应拆出独立的场景配置、状态管理和动画控制模块。
- 如果需要复杂手势、拖拽、时间轴编辑器或组件库级别的复用，再考虑 React/Vite/TypeScript。
- 如果需要高精度地理图层、缩放、坐标投影和大量地图元素，再评估 MapLibre 或 Canvas 地图库。

结论：当前架构足以承载“体验导演层”的第一阶段落地，不需要立刻更换技术栈。更合理的路线是先在现有静态前端中抽出 `scene`、`emotion`、`action`、`feedback` 四类配置；当配置和状态复杂度超过单页可维护范围时，再升级为独立前端工程。

- `interactionEvent`：用户触发行为，例如 hover、scroll、drag、tap、swipe、longpress。

### 24.1 从功能驱动改为场景驱动

后续主路径不再以“地图、压力 HUD、章节图谱、证据抽屉、哲学透镜、判断卡”这些模块为第一层结构，而应以场景为第一层结构。

建议主路径：

```text
天下显影
-> 北边急报
-> 长安聚焦
-> 未央宫入场
-> 朝堂争论
-> 竹简证据
-> 霍光沉默
-> 退朝案牍
-> 天下未定
```

模块不是消失，而是退到场景背后。用户看到的是“正在发生的事”，不是“可点击的功能集合”。

### 24.2 地图作为唯一持续存在的空间对象

地图不应只是开场页或背景图，而应成为贯穿体验的连续空间：

- 开场是天下地图。
- 北边急报时镜头移动到边塞。
- 压力汇聚时镜头推向长安。
- 进入朝堂时地图退为低层空间记忆。
- 退朝后镜头重新拉回天下。

这样用户始终知道自己身处哪里，页面切换的割裂感会明显降低。

实现上不要求真实 3D，也不要求复杂 GIS。第一阶段可以用 SVG 地图、CSS transform、分层遮罩和镜头状态完成。

### 24.3 自然交互：点击不是唯一入口

桌面端可以增加更自然的探索方式，但必须保留按钮兜底：

- Hover：经过边塞、长安、盐铁资源点时出现一句短提示。
- Scroll：推动镜头从天下进入长安，或从朝堂退回天下。
- Drag：轻微拖动地图时显出运输线或压力流。
- Tap：移动端点击仍是主入口。
- Swipe：移动端可左右切换阶段，但不能成为唯一入口。
- Longpress：查看出处或地点说明，但必须有普通点击替代路径。

原则：自然交互负责增强沉浸感，明确按钮负责保证可用性。

### 24.4 信息密度与视觉节奏

任何时刻最多保留三个视觉焦点：

```text
主视觉
当前事件
主动作
```

视觉节奏应有收放：

- 地图开场：信息少，制造好奇。
- 北边急报：信息突然压入，制造紧张。
- 朝堂争论：信息密度上升，制造判断压力。
- 霍光沉默：信息清空，制造压抑。
- 退朝案牍：信息重新收束，制造反思。

如果每一屏都一样热闹，用户会疲劳；如果每一屏都有不同的轻重，体验才像一段历史现场。

### 24.5 历史压力从 HUD 变成动态流

压力 HUD 可以保留，但不应只靠数字和进度条表达。建议把压力可视化为地图上的动态流：

- 北边军费：暗红色流线向长安汇聚。
- 盐铁收入：青铜绿色流线进入府库。
- 民生负担：赭黄色压力从地方扩散。
- 均输路线：运输线缓慢移动。
- 权力遮蔽：黑色或暗色遮罩覆盖朝堂部分区域。

第一阶段可用 SVG stroke-dashoffset、CSS animation 和透明度变化实现，不需要生成视频动画。

### 24.6 证据实物化，人物表演化

证据不应只是按钮或抽屉。建议在地图或朝堂中出现可感知的物件：

- 竹简：短证据。
- 奏章：政策依据。
- 案卷：长文史料。
- 印记：关键判断被记录。

人物首次出现也不应是资料卡，而应是发言或动作：

```text
桑弘羊：
边费不可一日废。
```

人物背景、关系和身份说明可以后置到旁路，避免用户第一次见到人物时像在读百科。

### 24.7 三层即时反馈

每次关键交互至少有三层反馈：

1. 视觉反馈：地图点亮、路线流动、竹简展开、朝堂变暗。
2. 状态反馈：压力、立场、判断轨迹发生变化。
3. 声音反馈：短音效、音乐层次变化或静音。

文字解释放在最后出现。用户应先“感到发生了什么”，再“读到发生了什么”。

### 24.8 Motion Guideline

建议建立动效规范，而不是为每个模块临时写动画。

| 场景 | 动效 | 建议时长 | 说明 |
|------|------|----------|------|
| 地图显影 | fade + slow scale | 800-1200ms | 开场建立空间 |
| 镜头推进 | transform + ease-in-out | 700-900ms | 天下到长安 |
| 压力变化 | width/opacity easing | 450-650ms | 避免突变 |
| 运输流线 | stroke-dashoffset | 持续循环 | 表达因果 |
| 证据展开 | unfold/slide | 350-500ms | 竹简或案卷 |
| 人物发言 | fade + slight rise | 250-350ms | 保持克制 |
| 霍光沉默 | dim + audio ducking | 3000ms | 留白事件 |
| 退朝盖印 | stamp + fade | 800-1000ms | 仪式完成 |

所有动效必须支持 `prefers-reduced-motion` 降级。降级后仍保留场景顺序和文字信息。

### 24.9 Design System

建议把视觉系统沉淀为设计令牌，而不是散落在 CSS 中：

- 颜色：财政青铜绿、民生赭黄、战争暗红、权力黑、思想青灰、史料竹色。
- 字体：标题可用更有古籍感的宋体/明体风格，正文保持清晰易读，出处使用小字号。
- 图标：优先使用自绘或项目内统一 SVG 线描，不建议混用 Material Icon、Font Awesome 等现代软件图标。
- 层级：地图为底层，压力流为中层，当前事件和主动作在前层。
- 留白：沉默、退朝、证据展开前后必须有明确空白时间。

这套系统的目标不是“古风装饰”，而是让用户不用读说明也能辨认内容类型。

### 24.10 Director Layer 前端架构

建议新增确定性的 Director Layer。它不是 AI，也不是业务推理，而是前端体验调度器。

Director Layer 只回答四个问题：

```text
此刻用户应该看哪里？
此刻哪些 UI 应该消失？
此刻应该是什么情绪？
下一步什么时候推进？
```

建议场景配置结构：

```json
{
  "sceneId": "huo_silence",
  "cameraState": "court",
  "emotion": "pressure",
  "focus": "court_silence",
  "hiddenRegions": ["mapHotspots", "chapterGraph", "judgementButtons"],
  "primaryAction": "继续退朝",
  "motion": ["dimCourt", "pause"],
  "sound": "duck",
  "dwellMs": 3000,
  "evidenceRefs": ["hanshu_huo_guang_context"]
}
```

前端运行方式：

```text
用户动作
-> Director 读取当前 scene
-> 更新 camera / visible regions / motion / sound
-> 触发地图、压力、证据或人物反馈
-> 进入下一 scene
```

这样可以避免动画、音乐、布局、按钮各自为政。

### 24.11 前端架构承载判断

结论：当前前端架构可以承载 V3.9 的第一阶段，但不建议继续以“大型单页脚本 + 零散 CSS 动画”的方式堆功能。

第一阶段仍可保持静态发布和 GitHub Pages，不需要后端，也不需要立刻引入 React/Vite/TypeScript。前提是把现有前端拆成几个清晰模块：

- `scenes.config`：场景、情绪、主动作、停顿、证据引用。
- `director`：控制当前场景、可见区域、镜头、动作推进。
- `map-stage`：地图镜头、热点、压力流、运输线。
- `motion-tokens`：统一动效时长、缓动、降级策略。
- `audio-controller`：音乐分段、静音、音量渐弱。
- `reflection`：退朝判断轨迹和复盘反馈。
- `design-tokens`：颜色、字体、图标、层级。

如果不做这些拆分，当前架构短期仍能运行，但后续会出现三个问题：

- 场景越多，状态越难追踪。
- 动画越多，CSS 和脚本越容易互相影响。
- 移动端和桌面端体验差异越大，维护成本越高。

因此，真正需要的不是马上换框架，而是先做“静态前端模块化”。当场景数量、状态复杂度、多人协作和测试要求继续上升时，再评估升级为 Vite + TypeScript 或 React。

### 24.12 是否需要生成动画

需要动效，但第一阶段不需要生成视频动画。

建议优先使用代码原生动效：

- SVG 线条动画：运输流、压力流、路线显影。
- CSS transition/keyframes：地图推进、界面显影、盖印、暗场。
- Web Animations API：需要更精细控制时使用。
- 少量静态 SVG：竹简、印章、驿站、关隘、马车、城门。

不建议第一阶段生成长视频或复杂 Lottie：

- 难以和用户选择、压力状态、证据显示实时同步。
- 文件体积可能影响移动端加载。
- 后续改文案、改节奏、改证据时维护成本高。

可以生成或绘制的资产：

- 地图纹理。
- 竹简/案卷/印章等视觉素材。
- 少量图标。
- 开场背景氛围图。

核心交互动效应由前端代码控制，而不是由视频替代。

### 24.13 是否需要使用其他大模型

第一阶段不需要引入其他大模型。

原因：
- 场景推进、情绪曲线、动效、声音和地图反馈都应是确定性的前端编排。
- 历史事实和证据边界已经由证据包控制，不应在运行时交给模型生成。
- 动画可以用 CSS/SVG/Web Animations 实现，不需要视频生成模型。

可以考虑使用其他模型的场景：

- 生成一次性的视觉资产草图，例如地图底纹、竹简纹理、印章风格参考。
- 生成音效或氛围音乐草案，但必须人工筛选和压缩。
- 生成不同风格的图标方案，再由前端转成稳定 SVG。

不建议使用模型的场景：

- 运行时生成历史发言。
- 运行时生成证据解释。
- 运行时生成用户判断结论。
- 运行时生成视频动画。

原则：模型可以辅助制作素材，但不能成为历史现场的实时事实来源，也不能替代前端的确定性体验编排。

### 25.1 地图即 UI，而不是地图旁边还有 UI

后续应把地图从“背景/模块”提升为产品主界面。用户的关键操作尽量发生在地图上，而不是地图旁边的功能面板里。

示例：

```text
点击盐铁资源
-> 盐铁点亮
-> 运输线流向长安
-> 府库微亮
-> 财政压力缓慢下降
-> 出现一句旁白
```

这比“点击盐铁 -> 打开说明卡片”更接近历史现场。地图本身承担空间、因果、压力和行动反馈。

### 25.2 时间流：让地图不仅表现空间，也表现历史推进

盐铁会议不是静态空间，而是长期财政、边防和制度变化累积后的结果。地图应引入轻量时间流：

```text
武帝余响
-> 数年边费
-> 府库吃紧
-> 始元六年
-> 未央召议
-> 退朝之后
```

时间流不需要复杂时间轴。可以通过地图状态变化表达：

- 边关压力逐渐增强。
- 盐铁路线逐渐亮起。
- 长安压力逐步聚集。
- 会议开始后地图退为暗层。
- 退朝后地图重新拉远。

移动端可以采用竖向推进：用户向上滑动或点击继续，像看一部竖屏历史纪录片。

### 25.3 空间连续：证据和案牍不应让用户离开现场

证据、人物、案牍不再是“离开地图打开页面”，而是在同一历史空间中展开：

- 竹简在地图或朝堂上出现。
- 案卷从侧边或底部展开，但地图仍在暗层存在。
- 退朝案牍覆盖朝堂，但盖印后镜头退回天下。

空间连续的目标是让用户感觉自己没有跳出产品，而是在同一个历史现场里移动视线。

### 25.4 Scene Rhythm：控制信息量的收放

每个场景应明确自己的信息密度：

| 场景 | 信息密度 | 体验目的 |
|------|----------|----------|
| 天下显影 | 10% | 好奇 |
| 北边急报 | 30% | 紧张 |
| 长安聚焦 | 45% | 被卷入 |
| 朝堂争论 | 70-90% | 判断压力 |
| 霍光沉默 | 5% | 压抑 |
| 退朝案牍 | 20% | 反思 |
| 天下未定 | 0-10% | 余韵 |

产品不能一路输出内容。它需要收、放、停、再推进。

### 25.5 Visual Priority Engine

每一刻只允许一个最高视觉焦点：

```text
★★★★★ 当前焦点
★★☆☆☆ 次要上下文
★☆☆☆☆ 背景层
```

示例：
- 证据展开时，地图降亮度、HUD 停止动画、章节入口隐藏。
- 桑弘羊发言时，压力流线降速，当前发言成为焦点。
- 霍光沉默时，所有入口隐藏，只有暗场和短句。

这不是新的业务逻辑，而是 UI 层的注意力控制。

### 25.6 Cognitive Load Controller

建议新增认知负荷控制器，防止用户同时面对过多功能。

| 用户状态 | 系统行为 |
|----------|----------|
| 第一次进入 | 只显示地图、一句旁白、一个动作 |
| 连续打开 3 个证据 | 暂时隐藏章节图谱和哲学透镜 |
| 长时间停留 | 出现一句轻提示，不弹窗打断 |
| 完成一次判断 | 再开放下一层信息 |
| 移动端窄屏 | 隐藏所有旁路入口，只保留主动作 |

目标不是减少内容，而是让内容按用户能承受的节奏出现。

### 25.7 证据等级：一眼区分史实、解释与透镜

建议增加证据等级视觉，但不要做成“真假评分”。

示例：

```text
史料原文       最高权重
编年史记录     高权重
后世整理       中权重
思想透镜       解释视角
项目判断       用户需自行评估
```

视觉表达可以使用印记、颜色和标签，而不是星级评分，避免让用户误以为有精确概率。

### 25.8 人物状态，不等于人物建模

当前不建议做人物形象建模。

原因：
- 项目的核心不是角色扮演，而是历史处境与判断形成。
- 复杂人物建模会显著提高资产成本和维护成本。
- 不准确的人物形象反而容易削弱历史可信度。
- 霍光、桑弘羊、贤良文学的重点是立场、权力和语言，不是脸。

第一阶段人物表达应采用：
- 剪影。
- 印章。
- 席位。
- 语句。
- 墨迹。
- 暗场。
- 人物状态变化。

人物状态示例：

| 人物/群体 | 状态表达 |
|-----------|----------|
| 桑弘羊 | 坚定、被反驳后停顿、继续辩解 |
| 贤良文学 | 共情、质问、坚持民生立场 |
| 霍光 | 始终沉默、界面暗场、权力压迫 |
| 昭帝 | 御座/帷幕/召议，不必露面 |
| 用户身份 | 史官记录、案牍署名、立场轨迹 |

### 25.9 如果未来需要人物建模，应建模谁

只有在后续决定做“可视化朝堂舞台”或“三维沉浸朝议”时，才考虑人物建模。即便如此，也应先做低成本、符号化、非写实模型。

优先级如下：

| 优先级 | 对象 | 建议形式 | 原因 |
|--------|------|----------|------|
| P0 | 桑弘羊 | 2D 剪影/半身符号 | 财政立场核心人物 |
| P0 | 贤良文学代表 | 2D 群像剪影 | 民生批判不宜变成单一具体脸 |
| P0 | 霍光 | 暗影/席位/帷幕后轮廓 | 权力遮蔽应避免过度表演 |
| P1 | 汉昭帝/御座 | 御座、帷幕、宫灯 | 皇帝更多是制度位置 |
| P1 | 史官/引路人 | 2D 侧影或笔墨符号 | 承担引导与记录 |
| P2 | 财政官、边将、百姓、商人 | 身份剪影 | 用于用户身份，不必写实 |

不建议为《盐铁论》涉及的所有贤良文学、官员或地方人物做模型。那会把产品从历史体验变成角色资产工程。

### 25.10 如果需要建模，用什么软件

当前推荐工具分层：

| 目标 | 推荐工具 | 输出 |
|------|----------|------|
| 剪影、印章、线描图标 | Figma / Illustrator / Inkscape | SVG |
| 竹简、纸张、地图纹理 | Photoshop / Krita / Procreate | PNG/WebP |
| 低成本 2D 动画 | Rive / LottieFiles + After Effects | Rive/Lottie/JSON |
| 简单 3D 器物或朝堂空间 | Blender | glTF/GLB |
| Web 端 3D 展示 | Three.js | 浏览器实时渲染 |

如果未来必须做 3D，优先建模“器物和空间”，而不是人物脸：

- 未央宫朝堂空间。
- 御座/帷幕。
- 案牍、竹简、印章。
- 关隘、驿站、马车。

人物只做低细节剪影或背影，避免历史写实风险和资产成本膨胀。

### 25.11 音乐段落要求

完整体验需要 `5` 段主音乐。短音效另算，不计入主音乐段落。

现有三段式音乐可以作为 MVP 降级方案，但 V3.10 的正式体验应按五段主音乐设计。原因是产品有五个明确的情绪阶段：入场、压力、辩论、沉默、退朝。如果继续只用三段音乐，霍光沉默和退朝余韵会被压缩，情绪层次不够清楚。

五段主音乐要求：

| 编号 | 名称 | 使用场景 | 情绪目标 | 时长与循环 | 编曲要求 | 转场要求 |
|------|------|----------|----------|------------|----------|----------|
| M1 | 天下显影 | 开场地图、天下铺开、用户进入时代之前 | 空旷、好奇、略带陌生感 | 60-90 秒，可无缝循环 | 低密度；弱旋律；可有风声、低频铺底、少量古琴/箫色彩；不要强节拍 | 可在 2-4 秒内淡入 M2 |
| M2 | 边关压力 | 北边急报、军费、府库吃紧、压力汇入长安 | 紧张、压迫、局势逼近 | 45-75 秒，可循环 | 节奏略增强；低鼓或脉冲感；暗红战争氛围；避免影视化过度煽情 | 与地图压力流同步增强，可淡入 M3 |
| M3 | 朝堂辩论 | 桑弘羊、贤良文学、义利之辨、治道交锋 | 克制、密集、理性拉扯 | 90-120 秒，可长循环 | 中低强度；稳定节拍；适合长时间阅读和判断；不能抢对白和证据文本 | 进入证据时音量降低 15-25%，进入 M4 时突然抽空 |
| M4 | 权力沉默 | 霍光沉默、权力遮蔽、全场停顿 | 压抑、低频、近乎静音 | 20-40 秒，不强调循环 | 极低密度；可以接近无音乐，只保留低频、空间残响或一声钟/磬；禁止旋律铺满 | 从 M3 快速降噪进入，结束后不能立刻热闹 |
| M5 | 退朝反思 | 退朝案牍、自动书写、盖印、地图远退、天下未定 | 缓慢、反思、余韵 | 60-100 秒，可循环或自然结束 | 慢速；低音量；轻微收束感；适合用户阅读自己的判断变化 | 盖印时可叠短音效，最后 5-8 秒自然淡出 |

短音效需要 `6` 类：

| 音效 | 使用场景 | 要求 |
|------|----------|------|
| S1 边报抵达 | 北边急报出现 | 短、干净、有警觉感，不刺耳 |
| S2 运输启动 | 均输路线或盐铁路线开始流动 | 轻微车马/木轮质感，不要游戏化 |
| S3 竹简展开 | 证据发现、案卷展开 | 木质、纸/竹摩擦感，300-800ms |
| S4 压力变化 | 府库、边防、民生压力变化 | 低频或轻击，提示状态变化即可 |
| S5 朝堂静音 | 霍光沉默前后 | 音乐抽离或空气感变化，不一定是具体声音 |
| S6 退朝盖印 | 退朝案牍完成 | 清晰、短促、有仪式感 |

音乐制作总要求：
- 所有主音乐都必须支持无缝循环或自然淡出。
- 音乐不得压过旁白、人物发言、证据原文和出处。
- 每段音乐应提供静音等价体验：静音时仍能通过地图、动画、文字和停顿理解情绪。
- 文件应优先使用压缩后的 `mp3` 或 `ogg`，单段体积应控制，避免移动端首屏加载变慢。
- 不为每个身份、每个章节、每条证据单独制作音乐。那会让体验变碎，也会增加维护成本。

### 25.12 前端架构承载判断

当前前端架构可以承载 V3.10 的第一阶段，但需要做结构性拆分。

可以承载的内容：
- 地图常驻、镜头推进、压力流、证据展开。
- 视觉优先级控制。
- 认知负荷控制。
- 五段音乐切换。
- 剪影、印章、竹简等 2D 资产。
- 移动端竖屏场景推进。

需要改进的架构：
- 新增 `visual-priority-controller`：统一管理焦点、透明度、暗场和隐藏区域。
- 新增 `cognitive-load-controller`：根据用户行为控制信息开放节奏。
- 新增 `timeline-controller`：管理历史时间流和地图状态变化。
- 强化 `audio-controller`：支持五段音乐、短音效、淡入淡出和静音降级。
- 强化 `asset-registry`：统一管理 SVG、纹理、音效和可能的 GLB 资产。

如果只做 2D 场景、SVG 地图和代码动效，不需要更换框架。

如果要做以下能力，当前架构就不足：
- 3D 朝堂空间。
- 多角色动画调度。
- 大量可复用组件和复杂状态管理。
- 多端保存、分享和回放。
- 高级时间轴编辑或可视化导演台。

此时建议升级为：
- Vite + TypeScript 作为前端工程底座。
- React 或 Vue 用于组件化状态管理。
- Three.js 只用于空间、器物或低细节剪影，不用于复杂人物表演。
- 独立 assets pipeline 管理 SVG、WebP、音频、GLB。

### 25.13 是否需要其他大模型

当前不需要其他大模型。

可以使用模型辅助生成一次性素材草案，但不能作为运行时依赖：

- 地图底纹草案。
- 竹简、纸张、印章纹理草案。
- 氛围音乐参考。
- 图标风格探索。

不建议用模型生成：
- 历史事实。
- 人物发言。
- 用户判断。
- 实时动画。
- 写实人物脸。

原则：模型可以做素材草图，产品运行时必须是确定性的体验编排。

## 26. V3.11 历史现场、体验导演与单线程交互

任务标识：`YT-V3-015`

价值：把体验从“模块完整”推进到“现场成立”。V3.11 不再增加新的知识模块，而是让地图、证据、人物、判断和音乐都发生在同一个历史空间中；同时引入更明确的 Experience Director，让产品根据用户状态控制节奏、焦点和信息密度。

依赖：
- `YT-V3-013` 场景驱动、地图常驻与动效架构。
- `YT-V3-014` 空间连续、认知负荷、音乐与人物资产决策。
- 现有叙事地图、证据包、退朝案牍、身份选择、音乐与移动端地图优先入口。

允许修改范围：
- 本体验文档。
- 后续实施时可修改盐铁会议静态前端的导演层配置、地图交互、视觉焦点、颜色状态、字体层级、判断轨迹、移动端主路径和轻量探索入口。

禁止修改范围：
- 不新增史实结论。
- 不改变证据来源边界。
- 不引入运行时生成史实、人物发言或判断。
- 不把探索奖励做成游戏化成就系统。
- 不在移动端同时开放多个旁路面板。

输入：
- 最新 UX 评审意见：空间感、直接操作对象、地图认知锚点、减少页面切换、导演提示、信息密度减法、呼吸停顿、颜色参与交互、字体层级、地图热点三段反馈、判断成长感、探索奖励、移动端单线程、结束余味、Experience Director。

输出：
- 历史现场化界面原则。
- Experience Director 行为规则。
- 地图认知锚点与直接操作对象设计。
- 判断成长和探索奖励设计。
- 前端架构承载判断。

接口：
- `experienceState`：用户当前体验状态，例如 `first_entry`、`reading_evidence`、`fast_skip`、`long_idle`、`near_retreat`。
- `directorHint`：一句话导演提示，解释当前历史发展到哪里。
- `focusObject`：当前可直接操作对象，例如 `changan`、`salt_iron`、`transport_route`、`bamboo_slip`、`court_dossier`。
- `judgementArc`：用户判断变化轨迹。
- `explorationNote`：隐藏史官批注或后世评语。

### 26.1 界面目标：不是打开模块，而是进入同一历史空间

当前所有模块都应退到幕后。用户看到的不是“地图模块、证据模块、人物模块、判断模块”，而是同一个历史空间里不断发生的事：

```text
北边烽火亮起
-> 压力流入长安
-> 朝堂声音出现
-> 竹简从现场展开
-> 案牍覆盖朝堂
-> 地图拉远
```

体验判断标准：如果用户能明显感觉自己在不断打开面板、弹窗、抽屉和页面，说明“历史现场”还没有成立。

### 26.2 直接操作对象，减少按钮感

按钮仍然需要保留，但主体验应尽量让用户直接操作历史对象。

| 当前方式 | 改进方向 |
|----------|----------|
| 点击“进入朝堂” | 点击长安或未央宫镜头推进 |
| 点击“查看证据” | 点击地图/朝堂中的竹简或奏章 |
| 点击“继续” | 点击当前发言、案牍或地图焦点推进 |
| 点击“查看路线” | 拖动或经过路线时运输流显影 |
| 点击“完成” | 案牍自动书写并盖印退朝 |

原则：按钮是兜底路径；世界本身才是主要交互界面。

### 26.3 地图作为认知锚点

地图必须成为用户最后记住的东西，而不是被其他模块服务的背景。

后续所有关键对象都应依附地图：

- 人物立场从长安/朝堂位置出现。
- 证据从地图地点或朝堂案卷出现。
- 压力从北边、地方、盐铁路线流向长安。
- 判断结果最终盖回地图或案牍。
- 退朝后地图重新成为主视觉。

地图不消失，只改变层级：开场是主角；朝堂时是暗层；证据时是背景空间；退朝后重新拉远。

### 26.4 导演提示：一句话告诉用户历史走到哪里

用户不应只知道自己到了“第五幕”，还要知道这一步在历史争论中的意义。

导演提示只用一句话，不写说明文：

| 场景 | 导演提示 |
|------|----------|
| 北边急报 | 边费第一次压到长安案前。 |
| 桑弘羊发言 | 国家先说出了自己的难处。 |
| 贤良文学反击 | 民生开始反过来质问财政。 |
| 证据展开 | 这不是观点，是一条可回看的依据。 |
| 霍光沉默 | 真正的权力未必正在发言。 |
| 退朝案牍 | 你的判断也成为这场争论的一部分。 |

导演提示用于定位，不用于灌输结论。

### 26.5 呼吸停顿与 Silence Design

每个关键场景结束后应保留短暂停顿：

- 普通转场：0.6-0.8 秒无新信息。
- 证据展开前：0.4-0.6 秒等待。
- 人物发言后：0.8-1.2 秒留白。
- 霍光沉默：3 秒暗场。
- 退朝后：5 秒余味停留。

停顿不是拖慢体验，而是给用户形成判断的时间。高级感来自节奏，不来自一直动。

### 26.6 颜色参与交互，而不只是分类

颜色不仅区分内容类型，也应反映用户判断倾向。

示例：

- 用户持续支持财政逻辑：界面青铜绿比例上升。
- 用户更关注民生：赭黄和暖色权重上升。
- 用户对战争压力敏感：暗红压力流更突出。
- 用户警惕权力遮蔽：暗色遮罩和低饱和层级增强。

颜色变化必须克制，只作为气氛和反馈，不应让用户觉得系统在替他打分。

### 26.7 字体层级硬规则

后续视觉稿应强制拉开字体层级，避免整页都是接近字号。

建议层级：

| 类型 | 建议字号 | 用途 |
|------|----------|------|
| 场景标题 | 40-48px | 天下、长安、退朝等大场景 |
| 人物发言 | 28-32px | 桑弘羊、贤良文学等关键短句 |
| 当前问题 | 24-28px | 用户需要作出判断的问题 |
| 正文说明 | 16-18px | 中等解释 |
| 史证原文 | 15-17px | 可读但克制 |
| 出处 | 12-14px | 轻量辅助 |

移动端按比例收敛，但必须保持层级差异。

### 26.8 地图热点三段反馈

所有关键热点都应遵守三段反馈：

```text
第一段：对象变化
第二段：世界变化
第三段：解释出现
```

示例：

```text
点击盐铁
-> 盐铁点亮
-> 运输线流动，长安微亮
-> 出现一句：今日盐铁入官，府库稍缓。
-> 用户可展开证据
```

这比直接弹出文字更能让用户感到“世界活着”。

### 26.9 判断卡要有成长感

退朝案牍不应只是总结页，而应呈现用户判断如何变化。

建议记录：

- 初始倾向。
- 第一次动摇。
- 哪条证据造成变化。
- 哪个议题仍未解决。
- 最终判断。

视觉上可以画出一条判断轨迹：

```text
财政支持
-> 动摇
-> 民生压力上升
-> 权力警惕
-> 最终判断
```

用户应能看到“我不是完成流程，而是真的改变过一次看法”。

### 26.10 探索奖励：史官批注，不做成成就

可以加入少量隐藏探索点，但必须保持克制。

形式：
- 地图角落发现史官批注。
- 后世评论短句。
- 某条证据背后的出处补充。
- 退朝后出现一条未解问题。

禁止：
- 徽章。
- 积分。
- 排名。
- 收集型成就。

探索奖励的目的不是让用户刷内容，而是让用户觉得这个历史现场还有余地。

### 26.11 移动端单线程体验

移动端不应只是桌面版缩小，也不应同时给用户多个入口。手机端主路径永远保持：

```text
一个空间
一句旁白
一个动作
```

移动端策略：

- 地图全屏或近全屏。
- 证据、判断、章节均进入全屏沉浸视图。
- 旁路入口默认隐藏。
- 上滑/点击推进时间流。
- 所有手势都有按钮替代。
- 一次只做一件事。

移动端更像竖屏历史纪录片，而不是缩小后的 Web 应用。

### 26.12 结束后的余味

退朝后不应立刻结束，也不应马上跳分享或总结。

推荐节奏：

```text
案牍盖印
-> 音乐渐弱
-> 地图拉远
-> 天下未定
-> 停留 5 秒
-> 用户自己退出或查看案牍
```

最后 5 秒不要新增按钮、弹窗或推荐内容。让用户自己停一下。

### 26.13 Experience Director

Experience Director 是比 Director Layer 更靠近用户状态的体验控制器。它不负责历史事实，只负责此刻如何呈现。

行为规则：

| 用户状态 | 导演行为 |
|----------|----------|
| 第一次进入 | 只显示地图、一句话、一个动作 |
| 停留过久 | 缓慢提示下一个焦点，不弹窗催促 |
| 连续打开多个证据 | 隐藏章节图谱和哲学透镜，降低负荷 |
| 快速跳过剧情 | 补一句关键背景，避免断层 |
| 长时间阅读 | 暂停地图动画，进入静态阅读模式 |
| 即将退朝 | 降低音乐，隐藏 HUD，聚焦案牍 |
| 移动端窄屏 | 强制单线程，不开放多个面板 |

它相当于体验中的剪辑师：让每一分钟都知道该出现什么、隐藏什么、停多久。

### 26.14 前端架构承载判断

当前前端架构可以承载 V3.11 的第一阶段，但前提是继续做“静态前端模块化”，不能继续把逻辑散落在页面事件和零散 CSS 中。

可以承载的内容：
- 地图常驻。
- 对象直接操作。
- 三段热点反馈。
- 导演提示。
- 呼吸停顿。
- 判断轨迹。
- 探索批注。
- 移动端单线程。
- 颜色和字体层级调整。

需要补强的前端模块：

- `experience-director`：根据用户状态控制提示、隐藏、动画暂停和下一焦点。
- `focus-manager`：保证每一刻只有一个最高视觉焦点。
- `map-interaction-layer`：让长安、盐铁、运输线、竹简等对象可直接操作。
- `judgement-arc`：记录并绘制用户观点变化。
- `exploration-layer`：管理少量史官批注和隐藏补充。
- `mobile-single-thread-router`：移动端一次只开放一个场景。
- `reading-mode-controller`：长时间阅读时暂停动效、降低干扰。

不需要立刻更换技术栈的情况：
- 仍然是 2D 地图、SVG 动效、本地音频、静态证据包。
- 没有账户、分享、跨设备保存、复杂 3D 朝堂。
- 探索奖励数量少，且都是静态内容。

需要升级架构的情况：
- 场景数量大幅增加，状态难以维护。
- 要支持用户回放自己的完整体验。
- 要生成可分享的退朝报告。
- 要做 3D 朝堂空间或复杂角色动画。
- 要引入大量可配置导演规则。

升级建议：
- 短期：继续静态发布，但抽出模块化 JavaScript 和配置文件。
- 中期：升级为 Vite + TypeScript，保证状态和配置可维护。
- 复杂 UI 阶段：引入 React 或 Vue 管理组件状态。
- 3D 阶段：只在必要时引入 Three.js，优先用于空间与器物，不用于写实人物脸。

结论：V3.11 的体验改进可以在当前静态前端上落地第一版；真正的风险不是“技术不能做”，而是“如果不抽象体验导演、焦点管理和移动端单线程，后续会很快难维护”。

## 27. V3.12 体验引擎、状态机与静态承载边界

任务标识：`YT-V3-016`

价值：把 V3.4 到 V3.11 的体验建议收束成前端体验架构。此前文档已经明确了“地图常驻、视觉焦点、证据发现、沉默设计、移动端单线程”等方向，但如果继续以零散页面事件和功能模块推进，后续会越来越难维护。V3.12 的目标是把产品从“功能模块拼装”调整为“体验状态驱动”。

依赖：
- 已有盐铁会议静态页面、证据包、地图层、音乐控制和退朝案牍设计。
- V3.8 的体验导演、V3.10 的认知负荷控制、V3.11 的历史现场与单线程交互。

允许修改范围：
- 本体验文档。
- 后续实施时可修改盐铁会议静态前端的场景配置、状态机、地图层配置、HUD 分层、证据展示层和交互事件路由。

禁止修改范围：
- 不改史料结论。
- 不改证据包的真实性边界。
- 不引入运行时 RAG 或动态补写史实。
- 不在本阶段改公共 Schema、迁移、根配置和运行态数据。

### 27.1 当前问题：功能模块太强，体验状态太弱

当前产品可以概括为：

```text
地图 + 剧情 + 人物 + 证据 + 章节 + 判断卡 + 导演层
```

这些模块本身都合理，但它们仍然是功能模块。用户看到的是地图、按钮、抽屉、面板和卡片；而理想体验中，用户应该感到自己正在经历：

```text
天下显影 -> 边关压力 -> 入朝站位 -> 朝堂争论 -> 证据动摇 -> 权力沉默 -> 退朝反思
```

因此，后续调整的重点不是继续增加功能，而是把前端主轴从“用户点了哪个模块”改为“用户正处在哪个体验状态”。

### 27.2 建议调整后的前端体验分层

建议把前端架构调整为六层：

```text
History Layer
-> Knowledge Layer
-> Narrative Layer
-> Experience Layer
-> Interaction Layer
-> Presentation Layer
```

各层职责如下：

| 层级 | 职责 | 不负责 |
|------|------|--------|
| History Layer | 存放史料、人物、地点、时间、政策、原典依据 | 不决定页面怎么显示 |
| Knowledge Layer | 组织概念关系、争点关系、证据引用关系 | 不控制剧情节奏 |
| Narrative Layer | 决定五幕主线、场景顺序、关键转折 | 不直接操作 DOM |
| Experience Layer | 控制情绪、焦点、镜头、停顿、认知负荷 | 不改写史实 |
| Interaction Layer | 接收点击、悬停、滚动、触摸、键盘等用户行为 | 不自行决定最终展示 |
| Presentation Layer | 渲染地图、HUD、竹简、案牍、面板、音乐和动效 | 不持有复杂业务判断 |

这套分层的核心是：**历史内容、叙事顺序、体验节奏和 UI 呈现必须解耦。**

### 27.3 新增核心：Experience Engine

建议新增 `Experience Engine`，作为所有体验呈现的中枢。

它不负责史料，不负责生成内容，也不负责具体绘制 UI。它只回答四个问题：

- 此刻用户应该看哪里？
- 此刻哪些东西应该隐藏？
- 此刻应该是什么情绪和节奏？
- 用户这个动作应该触发提示、动画、证据、停顿，还是进入下一场景？

交互链路应从：

```text
点击地图热点 -> 直接打开 Drawer
```

调整为：

```text
点击地图热点
-> Interaction Layer
-> Experience Engine 判断当前状态
-> 决定反馈层级
-> Presentation Layer 呈现
```

例如，同一个“盐铁资源”热点，在不同状态下可以有不同反馈：

| 用户状态 | 展示方式 |
|----------|----------|
| 第一次经过 | 只显示一句提示 |
| 开场压力阶段 | 盐铁点发光，运输线流向长安 |
| 财政辩论阶段 | 展开 200 字解释卡 |
| 证据阶段 | 展开竹简原文和出处 |
| 用户连续打开多个证据后 | 暂时只给摘要，避免负荷过高 |

这样，证据不再和某一个固定 UI 绑定，而是根据体验状态被不同程度地呈现。

### 27.4 新增导演状态机

V3.12 建议增加 `Director State Machine`。它是整个体验的主状态，不再让各组件各自维护“当前到了哪里”。

推荐主状态：

```text
Opening
-> PressureRising
-> IdentityForming
-> Debate
-> EvidenceDiscovery
-> Silence
-> Reflection
-> Ending
```

每个状态至少输出：

- 当前场景。
- 当前情绪。
- 当前视觉焦点。
- 当前地图层。
- 当前音乐。
- 当前允许的主要动作。
- 当前隐藏的 UI。
- 是否允许打开证据。
- 是否允许进入章节图谱。
- 是否进入阅读模式。

示例：

```text
State: Silence
Focus: 霍光/御座/空白朝堂
Map: 降亮度
HUD: 全部隐藏
Music: 降到近乎无声
Primary Action: 无，等待 3 秒
Evidence: 禁止打开
Next: Reflection
```

这能保证“霍光沉默”不是一句文案，而是一次由画面、声音、停顿和隐藏 UI 共同构成的体验。

### 27.5 新增 Scene DSL

为了避免把导演逻辑写死在组件里，建议用配置描述每个场景。可以是 JSON、YAML 或普通 JavaScript 对象。

示例：

```yaml
id: pressure_border_report
state: PressureRising
emotion: tension
focus: map_north_border
camera: zoom_to_north_then_changan
mapLayers:
  - space
  - war
  - transport
music: pressure
hudMode: world_only
primaryAction:
  label: 入朝
  next: identity_question
secondaryAction:
  label: 查看边报
  target: evidence_border_cost
allowEvidence: limited
silenceMs: 1200
hidden:
  - chapterGraph
  - philosophyLens
  - judgementDock
```

Scene DSL 的价值是让后续体验调整变成“改配置”，而不是到处改 UI 代码。

### 27.6 HUD 分层：不要一个 HUD 承担所有信息

当前 HUD 容易变成信息堆叠。建议拆成三类：

| HUD 类型 | 内容 | 出现时机 |
|----------|------|----------|
| World HUD | 始元六年、边防、府库、民生、商贸、朝廷稳定 | 地图和全局压力阶段 |
| Scene HUD | 当前争论、当前发言者、当前场景提示 | 朝堂争论阶段 |
| User HUD | 用户身份、观点倾向、动摇原因、已记录判断 | 用户作判断或退朝阶段 |

原则：
- 同一时刻最多显示一种 HUD。
- 证据展开时，HUD 降级或隐藏。
- 移动端默认不显示完整 HUD，只显示一句场景提示。

### 27.7 地图升级为 Map Engine

地图不应只是背景图，也不只是热点容器，而应该成为体验空间。建议抽象为 `Map Engine`。

地图层建议包括：

| 地图层 | 用途 |
|--------|------|
| Space Layer | 长安、北边、郡国、关隘、道路等空间基础 |
| Resource Layer | 盐、铁、粮、府库、市场等资源关系 |
| War Layer | 边报、军费、粮草、烽火、压力流 |
| Politics Layer | 朝堂、御座、权力遮蔽、人物位置 |
| Ideas Layer | 儒法、义利、治道等思想争点 |
| Evidence Layer | 竹简、奏章、史官批注、原典出处 |
| User Trace Layer | 用户站位、判断变化、最终案牍印记 |

后续所有对象尽量依附地图出现。人物、证据、判断、压力和用户轨迹都从地图中长出来，而不是脱离地图变成独立页面。

### 27.8 信息容器从 Drawer 拆为四级

不建议继续让 Drawer 承担所有信息。证据、说明、原文、哲学解释的阅读深度不同，应该有不同容器。

推荐四级：

| 等级 | 名称 | 适合内容 |
|------|------|----------|
| 1 | Hint | 一句话提示，如“边费正在压向长安” |
| 2 | Card | 100-200 字解释，如某个政策的即时意义 |
| 3 | Panel | 400-800 字材料，如一组证据和争点 |
| 4 | Document | 完整原文、六十篇图谱、长文阅读 |

交互原则：
- 用户第一次接触内容，只给 Hint 或 Card。
- 用户主动深入时，再进入 Panel 或 Document。
- 移动端 Document 必须全屏，不能用窄抽屉硬塞。

### 27.9 静态页面能否承载这样的项目

结论：**能承载第一阶段，甚至能承载一个完成度很高的 2D 沉浸式版本，但前提是必须从“单页脚本”升级为“静态模块化体验架构”。**

静态页面可以很好承载：
- 固定历史证据包。
- 确定性五幕剧情。
- SVG/Canvas 地图。
- CSS 动效和轻量镜头推进。
- Web Audio 音乐与音效控制。
- 本地用户状态。
- 退朝案牍的即时生成。
- GitHub Pages 静态部署。
- 移动端单线程体验。

静态页面的优势：
- 加载和发布简单。
- 没有服务器依赖。
- 历史事实边界稳定。
- 用户体验可控。
- 很适合“复原体验 Demo”和公开展示页。

但静态页面不适合长期承担：
- 用户账户和跨设备保存。
- 多次体验记录的云端复盘。
- 可分享的在线退朝报告。
- 运行时 AI 对话或动态史料检索。
- 大规模内容后台和可视化编辑器。
- 多人协作课堂或展馆后台。
- 复杂 3D 朝堂、写实人物动画和大量实时渲染资产。

因此，当前阶段不需要立刻上后端，也不需要马上引入 React、MapLibre 或 Three.js。真正需要的是把静态页内部先拆成清晰模块。

### 27.10 推荐技术路线

短期仍保持静态发布，但按以下方式重构前端组织：

```text
/data
  evidence_pack.json
  scenes.json
  map_layers.json
  music_cues.json

/engine
  director-state-machine.js
  experience-engine.js
  focus-manager.js
  cognitive-load-controller.js
  audio-director.js

/interaction
  map-interactions.js
  gesture-router.js
  evidence-router.js

/presentation
  map-view.js
  hud-view.js
  evidence-view.js
  judgement-view.js
  mobile-view.js
```

中期如果场景和状态继续增加，建议升级为：

```text
Vite + TypeScript + 状态机配置 + 自动化 UI 测试
```

只有在以下情况出现时，再考虑 React/Vue：
- 组件数量明显增加。
- 多个复杂面板要共享状态。
- 需要大型可配置后台或编辑器。
- 多人协作开发导致单页 DOM 操作难以维护。

只有在以下情况出现时，再考虑 Three.js：
- 需要真正的 3D 朝堂空间。
- 需要镜头穿行、器物空间、座次空间。
- 需要把地图、宫殿、案牍做成连续 3D 场景。

不建议为了“高级感”提前做 3D 写实人物。当前阶段人物仍应优先使用剪影、座次、印章、发言状态、声音和停顿来表达。

### 27.11 调整后的目标架构

如果面向未来产品化，可以采用以下结构：

```text
MetaOS Core
  |
History Engine
  |  史料、人物、地点、政策、原典依据
  |
Knowledge Engine
  |  争点关系、证据关系、思想关系
  |
Narrative Engine
  |  五幕主线、场景顺序、关键转折
  |
Experience Engine
  |  情绪、焦点、镜头、节奏、认知负荷
  |
Interaction Engine
  |  点击、悬停、滚动、触摸、地图热点
  |
Presentation Engine
  |  Web、Mobile、大屏、静态发布
  |
SVG / Canvas / CSS Animation / Web Audio
```

这套架构的核心收益：
- 同一套史料可以输出不同体验模式。
- 历史内容不被 UI 逻辑污染。
- 证据展示可以根据用户状态渐进展开。
- 地图、音乐、动画、HUD 和案牍由同一个状态机调度。
- 后续接入 MetaOS 时，Experience Engine 可以复用到其他历史复原、经典阅读和思想实验产品。

- `YT-V3-016E`：设计 `Map Engine` 图层清单和对象依附规则。

## 28. V3.13 业务闭环、交互显示与技术架构收敛

任务标识：`YT-V3-017`

价值：把前几轮分散的 UX、交互、界面和架构建议进一步收敛为“业务架构”和“技术架构”两条改造线。当前产品已经不缺体验创意，真正风险是能力过多、入口过多、状态过多，导致用户第一次进入时不知道自己到底是在经历朝议、浏览资料，还是使用研究工具。V3.13 的目标是明确唯一主体验，冻结核心业务对象，并给出静态前端下一步可执行的技术拆分方案。

依赖：
- V3.12 的 `Experience Engine`、`Director State Machine`、`Scene DSL` 和静态承载边界。
- 已有叙事地图、证据包、五幕主线、争点图谱、哲学透镜和退朝案牍设计。

允许修改范围：
- 本体验文档。
- 后续实施时可修改盐铁会议静态前端的主路径配置、业务对象说明、状态管理、场景配置、交互反馈、阅读模式、会话恢复和测试计划。

禁止修改范围：
- 不改变史料事实。
- 不让用户选择改写真实会议结果。
- 不让哲学透镜混入史实证据。
- 不在当前阶段引入后端账户、运行时 AI、动态 RAG 或大型内容后台。

### 28.1 核心判断：从“能力完整”转向“体验闭环”

当前产品已经拥有很多能力：

- 叙事地图。
- 五类历史压力。
- 身份进入。
- 五幕主线。
- 六十篇争点图谱。
- 哲学透镜。
- 证据抽屉。
- 判断轨迹。
- 情绪曲线。
- 音乐和环境音。
- 体验导演。
- 当代回声。

这些能力单独看都成立，但不应在首次体验中并列出现。第一次进入产品的用户不需要知道产品有多少模块，只需要知道自己正在经历什么、下一步要做什么、自己刚才的选择造成了什么变化。

因此，产品应分成两个空间：

| 空间 | 目标 | 内容 |
|------|------|------|
| 主体验 | 经历一次朝议 | 压力发生、首次取舍、立场形成、朝堂冲突、证据动摇、退朝案牍 |
| 深度探索 | 理解历史结构 | 六十篇争点图谱、证据检索、哲学透镜、权力关系、后世评价、当代回声 |

主体验建议控制在 5 到 8 分钟。深度探索不应在主体验中频繁打断用户，而应在用户主动进入或退朝后集中开放。

### 28.2 主体验业务闭环

建议将产品唯一主业务闭环定义为：

```text
历史处境
-> 用户初判
-> 立场进入
-> 争论经历
-> 证据接触
-> 判断变化
-> 退朝反思
```

这个闭环比“地图 -> 人物 -> 证据 -> 图谱 -> 判断卡”更适合作为业务主线。地图、音乐、图谱、透镜和证据都是支持能力，不是并列主业务。

### 28.3 交互设计调整

#### 28.3.1 从点击功能改为操作历史对象

后续主路径应尽量减少功能按钮，改为直接操作历史对象。

推荐交互：

- 点击北边急报，而不是点击“查看边防背景”。
- 点击均输路线，让车队或流线进入长安。
- 点击府库，让库存压力发生变化。
- 点击史官落下的竹简，再进入原文。
- 点击御座或空白朝堂，进入权力沉默。

统一链路：

```text
用户触碰历史对象
-> 现场先发生变化
-> 系统给出一句解释
-> 用户决定是否深入证据
```

避免链路：

```text
点击按钮
-> 弹出长文字
-> 关闭
```

#### 28.3.2 每次选择至少三层反馈

用户每次作出选择后，至少反馈三层：

| 反馈层 | 示例 |
|--------|------|
| 现场反馈 | 地图亮度、运输线、府库、朝堂压力变化 |
| 意义反馈 | “边防暂缓，府库更空” |
| 轨迹反馈 | 悄悄写入判断轨迹，退朝时回放 |

不建议直接显示“财政主义 +10”或“儒家倾向 +20”。这会把体验变成测试题。

更适合显示：

```text
你保住了边粮，但还没有回答民户还能承担多久。
```

这种反馈既让用户看到后果，又保留判断空间。

#### 28.3.3 身份生成不要像人格测试

身份生成可以保留，但不应输出机械匹配度。

不建议：

```text
你的选择更接近财政官，匹配度 78%。
```

建议：

```text
你首先选择保住边防。今天，你将从掌管府库的人所面对的压力进入朝堂。
```

身份是叙事入口，不是对用户人格的定义。首次体验中不建议随意切换身份，否则立场成本会消失。退朝后可以开放“第二视角”。

#### 28.3.4 证据系统采用阅读深度阶梯

证据不应只有“打开/关闭”。建议采用四级阅读深度：

| 层级 | 内容 | 推荐长度 |
|------|------|----------|
| 证据印记 | 来源名称和一句摘要 | 20-40 字 |
| 竹简摘要 | 原文短摘、白话转述、为何相关 | 100-180 字 |
| 案卷详情 | 完整定位、上下文、边界说明 | 300-600 字 |
| 深度阅读 | 全文结构、关联章节和检索 | 独立页面 |

默认只出现前两级。只有用户主动深入，才进入案卷详情和深度阅读。

同时，史实证据、思想透镜、策展解释和用户判断必须有明显不同外观：

| 信息类型 | 视觉建议 |
|----------|----------|
| 史实证据 | 纸色、直角印记、来源章 |
| 思想透镜 | 冷灰或青色、镜纹 |
| 策展解释 | 中性色、虚线边框 |
| 用户判断 | 手写墨迹或朱批 |

用户不读说明，也应能判断信息性质。

#### 28.3.5 中途退出与恢复

5 到 8 分钟体验仍可能被打断。应支持本地恢复。

建议记录：

- 当前场景。
- 初始选择。
- 已看证据。
- 当前观点轨迹。
- 是否开启声音。
- 减少动态效果设置。

再次进入时不弹普通浏览器提示，而以历史语境恢复：

```text
上次退在“民生反击”。案卷仍在堂侧。
```

动作：

- 继续入朝。
- 重新开始。

#### 28.3.6 停顿要有力量，也要可恢复

“霍光沉默三秒”有表现力，但不能让二次体验用户烦躁。

规则：

- 首次体验完整停顿。
- 再次体验缩短为 1 秒，或允许点击继续。
- 开启减少动态效果时，不强制黑场动画。
- 自动书写和镜头推进可以跳过，但不能跳过关键判断内容。

### 28.4 界面显示效果调整

#### 28.4.1 从“一屏一个焦点”升级为“一屏三要素”

每个场景必须明确：

```text
主视觉：用户先看什么
主问题：用户此刻想什么
主动作：用户接下来做什么
```

例如“北边急报”：

| 要素 | 内容 |
|------|------|
| 主视觉 | 北境与中断的粮道 |
| 主问题 | 边防是否继续投入 |
| 主动作 | 调粮 / 暂缓 |

除这三项以外的内容全部降级或隐藏。

#### 28.4.2 HUD 按场景渐进出现

边防、府库、民生、商贸、朝廷稳定五项压力有价值，但不能长期全部常驻。

建议：

| 阶段 | HUD |
|------|-----|
| 序章 | 只显示边防、府库 |
| 民生反击 | 加入民生 |
| 均输争论 | 出现商贸 |
| 权力遮蔽 | 朝廷稳定替代次要项 |
| 退朝 | 五项一起出现，用于回顾 |

HUD 应参与叙事，而不是固定仪表盘。

#### 28.4.3 压力不要只用进度条

连续进度条容易让产品像策略游戏。建议混合表达：

| 压力 | 可视化方式 |
|------|------------|
| 边防 | 北境暗红脉冲、烽火频率 |
| 府库 | 仓印逐渐空缺 |
| 民生 | 户籍纸张变暗、负担纹理加重 |
| 商贸 | 运输线路断续 |
| 权力 | 可操作区域逐渐收窄或压暗 |

只有退朝总结时，再转换为可比较的简洁图形。

#### 28.4.4 控制古风装饰比例

建议采用：

```text
80% 现代可读界面 + 20% 历史语义细节
```

规则：

- 正文使用高可读宋体或现代衬线体。
- 标题和章名可略有古意。
- 不用篆书承担按钮和长标题。
- 竹简只用于关键证据发现，不用于所有卡片。
- 印章只用于确认、证据来源和退朝，不要到处出现。

#### 28.4.5 地图保持空间连续，不必永远完整可见

“地图常驻”的目标是空间连续，不是要求完整地图永远占屏。

建议：

- 入朝时地图收拢为长安轮廓或背景纹理。
- 阅读证据时地图暂停并降至极低对比度。
- 退朝后再重新展开天下。
- 返回时镜头自然退回，不用硬切页面。

用户要记得自己从地图进入，但不必每一秒都看到完整地图。

#### 28.4.6 移动端避免过多隐藏手势

移动端可以有手势，但核心路径不能依赖隐藏手势。

规则：

- 核心路径始终保留明确主按钮。
- 上滑只用于扩展底部抽屉。
- 不用左右滑切换不可逆场景。
- 不把长按作为查看出处的唯一方式。
- 关键热区至少 44px x 44px。
- 底部主动作固定在安全区上方。

#### 28.4.7 增加阅读模式

用户展开较长原文时，应自动进入阅读模式：

- 背景降低对比度。
- 动画、音乐、HUD、地图流动暂停或降低。
- 行宽控制在 28 到 36 个汉字。
- 原文、白话、出处分层明显。
- 关闭按钮改为“回到现场”。
- 返回后恢复之前的镜头和音乐位置。

这能解决“沉浸体验”和“史料阅读”互相打断的问题。

### 28.5 业务架构调整

当前业务架构最大的不足，是把许多内容定义成了功能区，却没有把“用户经历一次历史判断”定义为核心业务对象。

建议新增以下业务对象。

#### 28.5.1 HistoricalExperience

一次完整体验实例，记录：

- 体验版本。
- 当前场景。
- 开始状态和结束状态。
- 初始取舍。
- 生成视角。
- 是否完成。
- 声音、阅读和辅助设置。

#### 28.5.2 JudgmentTrace

记录判断如何形成，而不是只保存最终判断：

- 初始判断。
- 每次动摇或坚持。
- 触发变化的场景。
- 关联证据。
- 最终判断。
- 剩余疑问。

#### 28.5.3 SceneDefinition

定义业务意义上的场景：

- 此场景要呈现的历史处境。
- 核心冲突。
- 允许动作。
- 对应证据。
- 历史结果是否固定。
- 用户行为只改变视角，还是影响体验反馈。

#### 28.5.4 EvidenceEncounter

记录用户如何接触证据，而不是简单记录“打开过”：

- 主动发现还是剧情推送。
- 看到摘要还是原文。
- 停留时间。
- 是否导致判断变化。
- 信息类型是事实、解释还是透镜。

#### 28.5.5 RetirementDossier

将“退朝案牍”提升为核心交付物，类似 MetaOS 的判断卡，但服务历史体验：

```text
RetirementDossier
- 初入朝堂时的判断
- 生成的进入视角
- 关键选择
- 首次动摇
- 使用过的史证
- 使用过的思想透镜
- 最终判断
- 未解决矛盾
- 与当代问题的谨慎联想
```

产品价值不只是“看完历史动画”，而是形成一份有证据边界的个人历史判断。

### 28.6 固定历史与可变体验边界

业务架构必须冻结以下边界。

不可变：
- 真实历史事件。
- 人物身份与已证实行为。
- 会议结果。
- 史料原文。
- 证据等级。
- 已知时间和地点。

可变：
- 用户进入视角。
- 信息出现顺序。
- 默认镜头。
- 压力感知权重。
- 证据发现路径。
- 观点变化轨迹。
- 最终反思表达。

不应出现：
- 用户选择改变会议结果。
- 叙事压力值冒充真实统计。
- 哲学材料被当作会议证据。
- 为了戏剧效果补写人物心理和发言。

### 28.7 当代回声暂缓进入主流程

“当代回声”有价值，但容易破坏历史沉浸，也容易让外部内容质量反向影响主体验。

建议：
- 不进入首次主流程。
- 退朝完成后才开放。
- 明确属于延伸讨论，不属于历史复原。
- 不自动写入退朝案牍。
- 如需引用，必须由用户主动选择“加入我的后续思考”。

### 28.8 双层验收指标

后续验收不应只看用户能不能打开页面，也不只看用户能否回答知识点。建议增加认知结果与体验过程双层指标。

认知结果：
- 是否理解双方核心理由。
- 是否能区分事实、解释和透镜。
- 是否能指出至少一个未解决矛盾。
- 是否形成了自己的判断。

体验过程：
- 首 30 秒是否理解自己要做什么。
- 首次关键操作是否在 10 秒内发生。
- 主线完成率。
- 证据打开率。
- 发生至少一次观点变化的比例。
- 移动端浮层遮挡率。
- 中途退出后的恢复率。

### 28.9 技术架构调整

结论：当前不需要立即切换 React、引入 GIS 平台或建设后端工作流，但必须停止继续把场景、动画、按钮、音乐和证据逻辑写进同一个页面脚本。

#### 28.9.1 从单页面脚本改为模块化静态前端

建议目录结构：

```text
/yantie
  /content
    evidence-pack.json
    scenes.json
    lenses.json
    map-layers.json

  /domain
    evidence-model.js
    judgment-trace.js
    experience-session.js

  /engine
    director-state-machine.js
    experience-engine.js
    scene-resolver.js
    cognitive-load-controller.js
    audio-director.js

  /interaction
    action-router.js
    map-interactions.js
    gesture-router.js

  /presentation
    map-view.js
    scene-view.js
    hud-view.js
    evidence-view.js
    dossier-view.js

  /styles
    tokens.css
    layout.css
    motion.css
    accessibility.css
```

这不改变静态发布能力，但能显著降低维护风险。

#### 28.9.2 建立单一 ExperienceState

建议统一维护：

```text
ExperienceState
- sessionId
- sceneId
- phase
- emotion
- focusTarget
- perspective
- pressureState
- visitedEvidence
- judgmentTrace
- audioState
- accessibilityState
- overlayState
```

地图、HUD、声音、证据和按钮全部根据该状态渲染，不得各自维护“当前幕数”和“当前焦点”。

#### 28.9.3 Director State Machine 只负责合法转移

推荐主状态：

```text
Opening
-> PressureRising
-> FirstChoice
-> PerspectiveFormed
-> CourtEntry
-> Debate
-> EvidenceDiscovery
-> PowerSilence
-> Reflection
-> Ending
```

状态机负责：
- 允许哪些动作。
- 下一状态是什么。
- 哪些 UI 必须隐藏。
- 是否允许打开证据。
- 是否进入阅读模式。
- 是否可跳过动画。

具体镜头、布局和动效不应塞进状态机，而应由 Scene DSL 和 Presentation Layer 决定。

#### 28.9.4 Scene DSL 保持小而稳定

第一阶段不要设计过度通用的“体验编程语言”。JSON 配置即可：

```json
{
  "id": "border_alert",
  "phase": "PressureRising",
  "emotion": "tension",
  "focus": "north_border",
  "mapLayer": ["base", "border", "supply"],
  "primaryAction": "allocate_supply",
  "allowedActions": ["allocate_supply", "hold_supply"],
  "evidenceRefs": ["evidence-017"],
  "presentation": {
    "layout": "map_event",
    "hud": ["border", "treasury"],
    "music": "narrative_tension",
    "motion": "border_pulse"
  }
}
```

第一阶段只支持主线所需字段，不做可视化编辑器，也不追求支持任意历史故事。

#### 28.9.5 事件与视觉效果解耦

用户动作先产生领域事件：

```text
SUPPLY_ALLOCATED
EVIDENCE_OPENED
JUDGMENT_REVISED
SCENE_COMPLETED
READING_MODE_ENTERED
```

`Experience Engine` 再把领域事件转换为体验效果：

```text
路线流动
压力变化
旁白出现
音乐减弱
打开案卷
```

这样以后更换动画或布局，不需要修改业务判断。

#### 28.9.6 增加构建时内容校验

由于产品坚持静态证据包和确定性编排，最值得建设的不是运行时 AI，而是构建时校验。

建议校验：
- 每个场景是否引用有效证据。
- 每条历史判断是否有证据类型。
- 哲学透镜是否明确标记非会议事实。
- 所有动作是否有合法状态转移。
- 是否存在无法到达或无法退出的场景。
- 每个场景是否只有一个主动作。
- 移动端主动作是否会被浮层覆盖。
- 退朝案牍所需字段是否都能从轨迹生成。

#### 28.9.7 本地会话恢复

静态版可以使用：

- `sessionStorage`：当前场景和临时浮层。
- `localStorage` 或 IndexedDB：未完成体验、判断轨迹和用户设置。

不存储整份证据包副本，只存 ID 与用户状态。

需要定义版本：

```text
experienceVersion
contentVersion
stateVersion
```

内容更新后，如果旧会话不兼容，应提示重新开始，而不是静默出错。

#### 28.9.8 测试拆分

至少四类测试：

| 测试类型 | 重点 |
|----------|------|
| 业务规则测试 | 历史结果不可被改写；透镜不能进入史实字段 |
| 状态机测试 | 场景可达、无死循环、不合法动作被拒绝 |
| 交互测试 | 主动作可见、证据可打开关闭、阅读模式可返回 |
| 视觉回归测试 | 桌面入场、移动端入场、证据全屏、霍光沉默、退朝案牍 |

#### 28.9.9 Vite/TypeScript 升级触发条件

不必立即迁移，但以下任意两项成立，就应升级：

- 场景超过 15 到 20 个。
- 状态转移超过 30 条。
- 前端模块超过 10 个。
- 需要会话恢复与版本迁移。
- 桌面和移动端出现明显不同的呈现逻辑。
- 两人以上并行开发前端。
- 需要稳定的自动化视觉回归。
- 单个页面文件仍超过 2000 到 3000 行。

升级顺序：

```text
原生单文件
-> 原生 ES Modules
-> Vite + TypeScript
-> 必要时引入轻量状态机库
-> 最后才考虑 React / Vue
```

React 不是 Experience Engine 的前提。先理清领域状态、场景配置和调度关系，再决定渲染框架。

## 33. A2 体验补强：退朝后材料导览与现代研究观点卡

本轮根据“材料导览有导无览”的反馈，调整退朝后探索的二层信息结构。材料导览不再只展示来源范围和使用边界，而是作为“材料地图”告诉用户：

- 这类材料回答什么问题。
- 具体应该看哪些材料线索。
- 它能帮助解释盐铁会议的哪一层冲突。
- 下一步应该进入全文争点、思想透镜，还是后世与当代讨论。

材料导览与思想透镜的分工保持清楚：

- 材料导览说明材料从哪里来、看什么、用来解释什么。

现代研究集中放入“后世与当代讨论”。界面展示作者、书目和观点摘要，例如 Gale、Loewe、Wagner、Lewis 等研究线索；不复制现代论文、译文、导言或专著正文。现代研究只用于退朝后延伸思考，不进入史证链、证据包或退朝案牍。

验收要求：

- 材料导览每张卡必须有“具体看什么 / 能解释什么 / 下一步”。

- 现代研究可以呈现作者及观点定位，但不能交付受版权保护的全文或长段摘录。
